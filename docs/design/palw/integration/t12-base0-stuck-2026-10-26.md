## 症状(監視 06:04〜06:08 UTC、llm host の公開 wRPC)
- BASE-0(`f1c5635c…`)の `receipt_licensed` 33 件。`getPalwClaims.deadlineDaa` は 15452〜15592 で、tip 15905 を過ぎている。Final にも void にもなっていない。

## 確定したこと
1. **表示されていた期限は誤り**。`palw_claim_phase_deadline_v1`(getPalwClaims の deadlineDaa)は licensed claim に対して `L + window_challenge` を返していた。一方 fold の DL-1(`palw_rcore_deadline_v1`)は、ADR-0160 F-Q の audit door(t12 は DAA 1,700 の ρ=10 flag day、`PALW_T12_POST_LAUNCH_FENCES_V3` で有効)で **credited claim には audit receipt が `k_aud` 件(ρ=10 で 1)揃うまで deadline を張らない**(`Some(None)`。待つだけで void も課金もしない)。BASE-0 だけが creditable(`palw_capacity_class_creditable_v1` = base class)。詰まった claim は `committedSompi=270` で、escrow 3.2e11 に対してコミットが credit で削られた credited claim である。つまり sweep は期限を飛ばしていない。sweep の skip(`palw_v2_expiry_held_v1`)は `rebound_daa` が無く court も開いていない claim には当たらない。int-13 の 4 fence もこの経路には触れていない。
2. **BASE-0 の producer hold は stall の原因ではない**。`getPalwProducerFacts` の詳細は「the base class … is the idle-only fallback: … the chain is normal (the last BLUE REAL attempt …) (ADR-0165: floors are refused until it is idle)」。REAL(ebf)attempt がある間は floor を出さないという設計どおりの挙動で、inflight の数え方やデッドロックではない。15472 以降に BASE-0 の新規 licence が無いのもこれで説明がつく。
3. **audit が来ない理由(node 側、可能性が高い)**: audit pool = operator 8 bond − producer − panel の 5 seat = **2 bond**。`palw_audit_duty` は「再生できない」(header 未保持・class 未解決・routing context なし)や「verdict なし」(replay の失敗・overdue)を `verdicts[claim] = false` として記録し、claim が候補である限り二度と再試行しなかった。turn は 30 DAA ごとに pool の次の member へ広がるが、pool は 2 しかない。このため一時的な失敗が 2 回あれば、その claim は永久に監査されず Final の deadline も張られない。fleet の node log(`cannot replay it` / `came to no verdict`)はまだ確認していない。**配備前に確認が要る。**

## 修正(規則は変えない、fence 不要、params/handshake id は不変)
- `kaspad/src/palw_audit_duty.rs`: verdict を `Reproduced / Refuted / Unjudged{retry_at}` に分けた。判定できなかった場合は `PALW_AUDIT_RETRY_DAA_V1`(= 1 turn、30 DAA)後に再試行する。Refuted は従来どおり最終判定。
- `consensus/core/src/palw_producer_v2.rs` `palw_claim_phase_deadline_v1`: audit 待ちの credited licence は `deadlineDaa = None` を返す(RPC 表示のみ。fold・deadline index・sweep は読まない)。
- consensus の判定はどちらも変えていない。過去の block の判定も変わらない。

## 追記(fleet log、ssh 読み取りのみ): 原因の確定
- 上記 3「一時的な失敗が永久化する」は **原因ではない**。36 時間の log で `cannot replay it` / `came to no verdict` は 0 件だった。再試行の修正は防御として残す。
- t12 の credited claim は **k_aud = 2**、pool は 2(例: 5d3744bd の pool は seat2 と seat5)。**2 bond の両方の receipt が要る。**
- seat5 は 5d3744bd を 10-25 06:42 に監査して receipt を出した(batch は block に載った)。
- **seat2 は 10-25 04:55 を最後に監査していない**。それ以降の log には `replay … waits: every replay slot is taken` が 1,411 回、`seat schedule: N duties due` が 1,547 回出ている。`audit_duty_tick_v1` は `seat_replays.has_room(false)` のときだけ replay を始める。seat duty が slot を占有し続けたため、seat2 の audit duty は 30 時間以上、一度も起動していない。この間 log は何も出さない(無言)。
- seat5 の 07:02 以降の無音は、自分の receipt を出し終えた後で候補が空になったため(`status.has_v1(me)`)。
