# RFC-0051 登録の読み取り RPC

2026-11-11。採択済み [RFC-0051](../../../rfc/0051-funded-preclaim-tokenizer-registration.md) の実装接続記録。公開 profile・activation の採択ではない。

## 入口

| RPC | wRPC op | gRPC request / response | 入力 |
| --- | --- | --- | --- |
| `getPalwTokenizerRegistrationQuote` | 221 | 1334 / 1335 | `openBodyHex`: canonical な署名前 Open body の Borsh hex。819 bytes / 1638 hex digits |
| `getPalwTokenizerRegistrationStatus` | 222 | 1336 / 1337 | `openId`: 64 bytes / 128 hex digits |

221・222 は未使用の C2 予約範囲から、本接続作業の coordinator が RFC-0051 の二つの参照 RPC に割り当てる。2026-11-11 に取得した `origin/main` と `origin/pre` はいずれも `244b69d93b8ac3fe259e6f33a187753798293bf0`。この両 ref、作業 HEAD、ローカル `rfc10/c2-panel` の `rpc/core/src/api/ops.rs` で未使用を確認した。既存の使用済み op・protobuf field の意味を変更しない。出荷前に統合先の番号を再確認する。

送信は既存 transaction RPC の責任であり、これらの RPC は署名・購入・送信を行わない。新規 Open cutoff 後も受理済み契約の status は読める。

## 共通の観測

両 transport は同じ version 1 response と `observationJson` を運ぶ。JSON 内の `schema` は 1。

- `acceptedParent`: 認証済み親の `block`・`daa`・`blueScore`。
- `acceptedParentRoot`: その親の state root。
- `prospectiveDaa`・`prospectiveBlueScore`: 見積もり用の virtual clock。受理 block として表示しない。

ノードは同じ virtual view を捕捉し、strict な親 state の復元・検証を完了する。旧形式の fallback を引用しない。応答前に同じ virtual owner と pruning/import epoch・親 identity を再照合する。状態が変わった場合や local capacity 不足は RPC エラーで再試行を要求し、通常の quote refusal に変更しない。全状態の root 計算を最終 virtual read lock 内では行わない。

## Quote

応答は `available`・`quoted`・`refusal`・`observationJson`。

成功の観測には Open ID、policy ID、canonical `policyHex` と `quoteHex`、宣言 key-event 数、署名 digest と purpose context、登録サービス焼却額、断片数、carrier bytes、scratch/work/保持量を含む。`slotsReserved=false`、`fundingVerified=false` を明示する。Part/Finish の割当 DAA は見積もりでは確定しない。

native Open と同じ parent pins・opener 資格・期限・cutoff・winner・料金・予約アルゴリズムを使う。期限処理後の book を有限の一時領域で検査し、捨てる。署名・UTXO の原資確認と予約の確定は実受理時に行う。既存 Open は再見積もりの成功にせず status の読み取りを要求する。

## Status

応答は `available`・`found`・`observationJson`。

受理された Open body、受理 point、保存済みサービス焼却額と charge ID、Part ごとの offset・length・予約 DAA・実受理 point、normal/recovery Finish の予約 DAA と試行済みフラグ、終端・予約解放・完了時の registration ID を返す。予約枠が存在することと、その Part が受理済みであることを分ける。raw Part bytes は返さない。

失敗した Finish の行には実行 block が保存されていないため、試行フラグから block を捏造しない。carrier txid・UTXO 総手数料もこの行には存在しない。`found=false` は当該親で unknown/not-retained であり、未送信・拒否・GC・reorg のどれかを断定しない。完了済み rooted registration が残っていても、GC 後の Open 履歴を復活させない。

## 上限と CLI

Open body と ID はサービス側で exact length を検査してから decode する。wRPC binary decoder は文字列長を検査してから確保する。gRPC は既存の transport message 上限に加え、変換時に長さを検査してから複製する。観測 JSON は最大 262,144 bytes、refusal は最大 8,192 bytes。status は一つの Open の有限 Part metadata だけを返す。

```sh
misaka palw tokenizer-registration quote --open-body ./open-body.borsh
misaka palw tokenizer-registration status <full-open-id>
```

`open-body.borsh` は SDK の `TokenizerRegistrationOpenBodyV1` を `borsh::to_vec` で符号化した署名前 body。carrier や署名済み Open は渡さない。CLI は snapshot と全欄を JSON で表示する。quote の refusal / dormant と接続エラーは非ゼロ終了、status の `found=false` は欠損を明示した読み取り結果。

実装コードの追加と公開読戻しの成功は別である。node、RPC service、gRPC client/server、wRPC server、CLI の cargo check と、core / RPC / gRPC / service の回帰22件が成功した。ローカルの機能検査であり、公開受理や性能資格ではない。詳細は [実装台帳](public-one-honest-implementation-ledger.md) に記録する。

## 署名済み payload の準備

```sh
misaka palw tokenizer-registration prepare \
  --open-body ./open-body.borsh \
  --raw-tokenizer ./tokenizer.json \
  --eog-opening ./eog-opening.borsh \
  --key-file ./opener.seed \
  --output-dir ./tokenizer-registration
```

EOG opening は `PalwTokenTableEogOpeningV1` の canonical Borsh。CLI は live quote の Open ID・policy・purpose を確認し、同じ native fee 計算と一致することを要求する。raw と EOG を有限長で読み、登録された opener 鍵との一致を確認してから SDK の raw/rendering 検査と署名を行う。秘密鍵の値を引数に渡さず、既存の key file/stdin 経路を使う。

新規ディレクトリへ `open.tkr1`、`part-0000.tkr1` 以降、`finish.tkr1`、最後に `quote.json` を作る。既存ディレクトリは上書きしない。書込みに失敗した場合、その実行で作成したファイルだけを削除し、残るディレクトリがあれば不完全と報告する。通常終了した bundle でも、UTXO の支払・送信・予約・公開受理は済んでいない。Part/Finish の送信には、実際の Open status から読んだ割当と受理済みの先行操作が必要である。

この追加は CLI の cargo check で確認した。公開 endpoint を使った prepare 実行と送信は未実施である。

## 一つの control の支払・送信

```sh
misaka palw tokenizer-registration send \
  --payload ./tokenizer-registration/open.tkr1 \
  --quote ./tokenizer-registration/quote.json \
  --key-file ./payer.seed \
  --max-fee <total-fee-ceiling-in-sompi>
```

既定は dry-run。支払者は opener と別の鍵でもよい。現在の Open quote または accepted status、元の Open ID/policy と control の署名、opener の active 状態と登録用担保下限を確認する。Open は新しい quote のサービス焼却額と通常手数料の和を支払い、Part/Finish の追加サービス焼却はゼロ。`--max-fee` は今回一つの carrier の合計上限である。実 UTXO と carrier mass から通常手数料を計算し、上限超過・資金不足では送信しない。

実送信には `--submit` を指定する。Part/Finish は現在の prospective DAA が元の予約枠と一致する場合だけ送信し、署名後・送信直前に親/quote/status が変化していないことを再読する。受理済み Part は再課金せず拒否する。Finish は先行する全 Part の受理を要求し、使用済み/過去の通常枠は元の recovery 枠に限って進める。新たな期限や枠は割り当てない。

出力は txid、Open ID、親 block/root、予約 DAA、通常手数料・登録料・総額を含む。`submitted=true` は transaction RPC が同じ txid を返したことを表す。`acceptanceConfirmed=false` のままであり、次の control へ進む前に status の受理 point を読む。CLI の live RPC・broadcast 通し検証は未実施。[Round と CLI の回帰記録](../../../evidence/palw/tokenizer-registration-round-sender-regression-2026-11-11.json)は、実ノードの Round と CLI の予約枠選択検査を分けて記録する。
