# testnet-12 DAA 14,000 リリース計画(2026-10-15 ユーザー決定)

**決定:** 稼働中の testnet-12 を、`pre` に載っている実装(RFC02・RFC06/07/08/12・G14・RFC-0015〜0019・ADR-0162〜0179)へ更新する。新規 fence は **DAA 14,000** で有効化する(当初案の DAA 12,000 から変更)。

## 進める順序(この順を崩さない)

1. **全部完了:** G14・RFC02・RFC06〜12・RFC-0019 のコード実装を完了し、統合ブランチ `integ/rfc02-rfc06-12-g14` へ集約する。
2. **一括検証:** 生成物の再現性 → cargo check(全段)→ 対象テスト → 影響スイート → clippy。未有効化時に旧ルールと同一であること(t12 の params id・指紋・A-2)を確認する。
3. **実ノード検証・測定:** RFC-0019 までに新しく実装した全経路と、ブロック生成を、ローカル devnet / 校正ネットワークで検証する。複数モデルの同時生成と RED 取り込み、Gate C、300M 閉鎖モデル攻撃試験、分断・再接続・IBD での収束、heartbeat/BASE-0 の継続も含める。測定値(V+ の σ/k、ADR-0176 の Q/B/R/F・予約額・burst、認証の m/k など)を記録し、測定値記録の gate を満たす。
4. **drill:** 出荷するバイナリそのもので、DAA 14,000 の fence をまたぐ drill を行う。fence をまたぐ drill 無しに出荷しない。
5. **承認後に配備:** ユーザー承認の後に、t12 のノード運営者へ配布・更新する。

## 原則

- 測定値の記録が無い仮の値のまま有効化しない(各 fence の measured-value gate)。間に合わない fence は、有効化対象から外して休眠のまま載せる(ユーザーに報告して判断を得る)。
- 有効化前は、旧バイナリと新バイナリが同じブロック・state root・fork choice になること。
- 永続決定: PRINCIPLES §8(計算の暗号学的証明を使わない)、§9(モデル二階層、モデル単位の検証は不採用、claim 単位の検証は全モデルで維持)。DNS-BFT は RFC-0012 方式 (b) で退役し、新しい規則は依存しない。
- 指紋が変わるリリースは origin/main へ fast-forward で push する(既存の運用則)。
