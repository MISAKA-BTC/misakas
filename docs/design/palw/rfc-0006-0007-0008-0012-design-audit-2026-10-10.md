# RFC-0006 / 0007 / 0008 / 0012 コード設計監査 — 2026-10-10

## 結論と対象

**4 RFC をまとめて有効化できる設計には、まだ達していない。** RFC6 の shard 構成と RFC12 の executed-prefix
証明は実装を継続できる土台がある。RFC7 の sampled approval は soundness / source participation / 経済条件の承認待ち。
RFC8 は支払い・canonical work・Final 後の責任追跡を接続する必要がある。テスト成功だけでこの判断は変わらない。

監査の基準は `docs/PRINCIPLES.md`、各 RFC、実装仕様、追加受入条件
`docs/palw-round-exec-additional-acceptance-2026-10-10.md`。開始時の checkout `1f98d3bf4` には対象の最新実装がなかったため、
integration `3730cc90f` を基点とするローカル branch `codex/rfc-6-7-8-12-design-audit` で評価した。
RFC8 round 3 は integration に入っていなかったため、`origin/rfc8/x8r-review` の `5c04fc473` を同 branch に取り込んだ。
元の integration branch、公開 preset、fence の高さは変更しない。

## 本監査で修正した欠陥

### RFC7: 同一 work を複数 source として混ぜられた

`misaka-palw-challenge/src/sealed.rs::collect_sealed_work_beacon_v3` は distinct producer を要求していたが、
`canonical_work_id` の重複を排除していなかった。異なる producer の seal で同一 work を再利用すると quorum を満たし得た。
また source の Final が reveal より前でも通った。

qualifying Final の work identity を集合で検査し、重複または時系列不整合なら **全試行を veto** する。
reveal 後に source を落として別の subset を選ぶ処理にはしない。入力 seal を逆順にした場合も同じ結果となる回帰テストを追加した。
この修正は source の独立性や参加確率の証明にはならない。

### RFC8: slice の切り方で同じ executor の報酬が変わった

`palw_work_slice_v2::settle_core_v2` は各 slice を個別に floor してから executor に足していた。
allocation 7、total work 10、同一 executor の work 8 は、1 slice なら 5、4+4 の 2 slices なら 4 になった。
executor ごとの work を checked arithmetic で合計してから一度だけ floor する。
full / partial settlement の双方について同じ分割の変更で同じ支払額になるテストを追加した。

### RFC8: 先払額を引いても slice leg の合計が予算残高を超えた

`palw_exec_v2_fold::settle_at_final_v2` は executor ごとの route advance を slice leg から引き、root leg だけを saturate していた。
prefix advance が prefix share を超える場合、slice legs + advance が allocation を超える。
新しい leg 全体を未使用残高で制限し、不足時は executor ごとに比例配分して整数端数を root に残す。
advance が allocation 全体を既に超えていれば、新たな支払いは 0。
既に支払った超過分を回収する修正ではないため、次節の無前払 hook は必須のままである。

### RFC12: open computation court が native settlement を止めなかった

evidence filtering / lifecycle closure / readiness が `da_sessions_iter()` のみを読んでいた。
通常の計算 court が開いている Final claim は、trace retention の時計が過ぎると Safe 側へ進め得た。
`native_open_sessions_v1` で DA と computation court の共通 inventory を作り、3 箇所を同じ入力にする。
JSON の `openDa` / `openDaSession` は既存の wire 名を維持し、説明文を dispute court に拡張した。
retention が過ぎても court が evidence と lifecycle を止め、court を除いた control では復帰するテストを追加した。

### 統合時の欠落

budget と EXEC が双方追加した state-root block / carriage tail / delta は片方を捨てずに保持する。
carriage tail は budget `0xEF`、EXEC `0xEE`、delta はそれぞれ 190/191 と 180/181。
lifecycle kind の既存 `ModelBondAllocationV1 = 5` を維持し、`ExecPayloadV2 = 6` にする。
RFC8 fixture の `ClaimRowV1` に現行の `sealed_daa` を補い、共通 conformance helper の fee-floor と Config 編集を両立する。
restart を検査する fixture の IR row に canonical program bytes と正しい長さ・hash を保持させる。
node の A-2 harness に新しい lifecycle / header fence の arm を追加し、landed row の exhaustive sweep に含める。
A-2 のテスト用高さを編集する経路のみで、公開 preset は変更しない。
A-2 の tag 109 を現行 wire form に再 pin し、RFC8 tag 130 の pin を追加する。tag 113 は現行 pin が一致した。
削除済み HA takeover の node-local `TakeoverToken` を NotCarried と分類し、live lifecycle wire の pin は変えない。

node の A-2 試験は、休眠中の kernel route / receipt に `palw_mempool_kernel_route_refusal` が適用される不具合も検出した。
各 object の lifecycle fence を確認してから route の拒否判定に進むよう修正した。未発効 object は既存の dormant 判定へ戻る。
G14 の EXEC fixture は OPV の salted seal 条件に追従していなかったため、既存の `seal_and_reveal` helper を使う。
同 fixture は 4〜5 件の reveal を一つの block に入れていたが、node の試験 budget 4 の半分は prosecution に予約され、
admission は 2 件まで。policy の空き枠ごとに reveal を分ける。REAL 抽選を除いた canonical prefix / continuation の
kernel admission 回帰も追加し、修正前は 4.75 秒の実行で同じ拒否を再現した。
本番の seal validation と canonical attempt target は緩めない。

## 有効化を止めるコード上の blocker

### BUDGET: root Final より前の route payout

`palw_kernel_route_fold_v1::apply_settlements` の `FinalReward` は `PayJobEscrow` の debit を根拠に直ちに
`add_kernel_payout` を呼ぶ。prefix / slice の kernel Final は root Final より先に来る。
`exec_v2_root_of_kernel_claim_v1` はあるが、この consumer は呼ばず、`budget-final` はコメントに留まる。
root 精算時に事後 netting しても、voided root から既払いを戻せない。
さらに `palw_exec_v2_route_reward_v1` は `rewarded` と policy の額を読むだけで、実際に debit / pay した額の journal ではない。

必要な変更は root の一つの reservation へ prefix / slice の全 reward path を関連付け、root Final まで escrow / vesting に保持すること。
root を宣言する前に prefix reward が払われた場合と、slice admission 前に kernel Final が来る場合も扱う。
acceptance / kernel Final / root Final / void / reorg / retirement の全経路に同じ debit と rollback を接続する。
必要なテストは途中 Final 後の root default、全 leg 0、部分 escrow、先払が一部 executor の share を超える場合、
duplicate Final と reorg 後の再 Final。事後の飽和減算を無前払 gate の PASS と扱わない。

### WORK: interval の大きさは実行から導出されていない

`apply_root_declared_v2` が prefix work を REAL claim の canonical weight と比較する一方、suffix の `total_work` / `boundaries`
は宣言から来る。`exec_v2_admit_slice_v1` は `planned.work()` を使い、verification binding は nonce / prompt / output /
state / DA を結ぶが、その kernel run の canonical IR cost を interval と比較しない。
tiny run を大きな interval として名乗れることを、署名・range nonoverlap・128 slice cap だけでは防げない。

必要な変更は registered IR / canonical job / execution positions から prefix と各 range の work を同じ単位で導出し、
total と boundaries を再計算すること。異なる model / context / decode の実行を同額と仮定しない。
宣言の work を増やした攻撃、同じ run を細分化した場合、別 producer / root への再利用、pruning 後の replay をテストする。

後続作業で `palw_exec_work_plan_v1` を導出規則の実行可能な参照として追加した。REAL の抽選込み weight と
execution cost を別量にし、登録 IR / 一つの whole-job facts / 絶対位置から prefix と各 suffix の 10 次元 vector を求める。
履歴の再実行を新たな useful work として数えない。既存の 2 cost policy の snapshot、context / slice 数 / `2^48` work の
上限、生成数と宣言 cost の照合を備える。**現在の fold / admission には未接続であり、WORK gate は未解決。**
既存 shape の飽和する中間演算にも checked 実装または validated bound の証明が必要。
仕様の補正と残る実装要件は `rfc-0008-implementation-spec.md` §12 に記録した。

prefix binding にも生成数の不足を発見した。REAL の exact decode が 1 でも、2 token の kernel job と、その出力を
1-token context に hash した REAL commitment が揃うと宣言を受理していた。修正前の fold regression で再現し、
job の maximum と実際の generated 長の両方を REAL context の nonzero exact decode と照合するよう修正した。

`job_work_id` が slice cuts と output-dependent initial state を含む点も未解決。切り方を変えて一回利用を回避しない
semantic job identity と、pruning 後も earliest legal reuse まで保持する bounded history が必要。root id を除外しただけでは足りない。

### WINDOW: settled root の依存 claim が後で convicted になっても伝播しない

`sync_slice_verification_v2` は prefix / slice 共に root phase を `Open | Complete` に限定する。
`void_prefix_v2` / `void_suffix_v2` も `Settled` を無視し、root claim の `Final` を再評価しない。
一方 kernel claim は Final 後も liability horizon 内の court / demand の対象となる。
`palw_state_v2::finalize_claim` は slice leg を `add_panel_payout` に渡すため、root producer の vesting と同じ回収経路にも乗らない。

必要な変更は依存 claim の court / retention / collectible liability を root まで保持し、Final 後の conviction / default を
root の safe weight、native evidence、未解放 vesting と payout 全体に一貫して反映すること。
root に `void_claim` だけを呼ぶ変更では safe weight / vesting の巻戻しが不足する。
Settled 後の prefix / 中間 slice conviction と post-Final demand default、再起動、reorg、pruned join の回帰が必要。

## 追加受入条件と政策判断

SLICE の fold テストには prefix reuse と duplicate kernel Final の回帰を追加した。これを real-node の同条件テストと同一視しない。
RECOVERY は既存 pipeline の restart / replay / sync list / reorg が対象だが、複数 process の実際の P2P / pruning は別 gate。
NEUTRALITY は fee-only Round の swap test と、operators / genesis / registration order による優先の否定が必要。
SPLIT は本修正により **同じ executor 内** の rounding 差を閉じる。複数 bond / model に資本を分けた経済的な Sybil neutrality は
BUDGET / ECON の試験を別途要する。ECON round 4 の UNKNOWN / FAIL を本監査で PASS に変更しない。

fee-only Round を `B_max` に数えるか別 execution cap にするか、market fee を `R_max` に入れるかは政策未決。
この監査は値や意味を新たに決めない。§6 の Final 前無支払、EVM / bridge export、reservation による同時 open claim cap、
pre-Final weight、DAA window 280–436 の validation が全 consumer に接続されることを activation 条件として残す。

## 完全解消を判定する要件の索引

対象を RFC8 の三つの blocker に限定しない。`docs/PRINCIPLES.md` と ADR-0173 / 0176 / 0177 を優先し、
各 RFC の全節・追加受入条件を次の群で追跡する。以下は追跡用の索引であり、各群の受入条件を省略・変更するものではない。
「mechanism が書かれている」「caller に接続した」「受入条件を証拠で満たした」を区別する。

受入証拠、残る activation 条件を個別に確定してから完全解消を判断する。
