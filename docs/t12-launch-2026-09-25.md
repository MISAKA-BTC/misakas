## 1. このリリースに入っているもの

- **R-core+(ADR-0152 v3.1)の全体。** Phase 2 の filer / court / DA / reporter、A-held、Activation Pool(R1/R2、P1〜P4)、readiness horizon 24、P3 の Candidate proof timing、EVM ブリッジ台帳。
- **mainnet 値。** λ 5、timestamp の tolerance 1,620 s、max_block_level 225。mainnet card は DNS 6 × 20M、carve 20% / 720‰、coinbase long maturity 600。
- **beat の先行時刻の上限。** heartbeat と clock step は、受信側の時計 + 132 s を超える stamp を拒否する(一時的な拒否で、キャッシュしない)。1 producer が DAA を一度に進められるのは 2 までになる。
- **execution lane の quantum maturity を 120 DAA に短縮。** round block は最初の Final の約 120 DAA 後から出る。
- **readiness の期限切れ対策。** 期限切れが近い seat の readiness 証明は、メモリ台帳や carrier の詰まりに関係なく必ず出す。floor の replay の見積もりから他 class の artifact を外す。
- **mempool の除去。** fold が拒否する H-1 carrier を、全ノードの mempool から毎 block 除去する。
- **node の義務は常に on。** panel、round lane、t12 の chain classes は起動オプションに関係なく動く。旧 flag は WARN を出すだけ。**1 つの bond は 1 つの process だけで動かすこと**(standby や登録用の 2 つ目の process を動かすと、round permit に二重署名して slash される)。
- **CLI の修正。** `palw da-accuse`、shard court、shard licensing が bond を正しく読むようになった。

## 2. 既知の問題(公開後に fence またはノード更新で修正する)

1. **heartbeat 透過による二重支払い(CRITICAL)**
   - bond を持たない heartbeat miner が、公開された attempt を自分の秘密の鎖に取り込むと、merge_depth(約 30 blue、約 10 分)の範囲で reorg できる。
   - 修正の branch は `rcore/hb-transparency-fix`(WIP)。
2. **panel seed の grinding(CRITICAL)**
   - panel の seed は anchor block の識別子になっている。そのため anchor の producer は、公開前に panel を引き直せる。
   - 外部の seat は、使えるようになるまでに 1,000 DAA の成熟が要る。修正はそれより前、**公開後 36 時間以内**に fence で入れる。branch は `rcore/panel-seed-exec-commitment`(WIP)。
   - それまでの間は、operator ごとの panel の偏りを監視する。
3. **DNS finality は Bootstrap の状態。** validator への資金は公開後に行う。それまで DNS の reorg gate は効かない。
4. **Final 後の Valid lock が、seat の 500‰ 枠を埋めていく(予測)。**
   - λ5 では、1〜3 日で bind できなくなる恐れがある。監視しながら、対策の設計を決める。
5. **全 seat が Valid を出したのに licence されない claim が出る(V04)。** 原因は特定済み: licence を出す collector が claim id の小さい順に出すため、id の大きい claim が待たされ続ける(待ちフラグが外れないことが増幅する)。node の更新で直す。最初の receipt 期限(bound+600、公開の約 22 時間後)より前に入れる。
6. **8k の readiness が落ちたときの被害の拡大(pre-t12 で DAA 52 に Held → claim 2 本が void)。**
   - このリリースで直したもの: 期限切れが近い seat の readiness 証明を必ず出す、floor の見積もりから他 class の artifact を外す、詰まった carrier を readiness 証明で置き換える、fold が拒否する carrier を全ノードの mempool から除去する。
   - まだ直していないもの: Held になると bind 前の claim をすぐ void する規則と Probation の進捗が 0 に戻る規則(V03/V05、fence で修正)、readiness 以外の義務の carrier が詰まったときの脱出と carrier 枠が 1 本しかない問題(V01 の panel 側・V07、ノード更新で修正)。
   - それまでは 8k の seat の readiness(`getPalwPanelSeats` の proved / expires、ログの `no proof —` と `waits for a carrier slot`)を監視し、詰まった seat は再起動で回復させる。
7. **その他の予定済みの修正**
   - Registry: NCP での組み直し、Probation の保持(`rcore/registry-resilience`)。
   - ブリッジ監査 BR-1〜BR-7(`rcore/bridge-fixes`)。
   - Position の sink の束縛、quoteSell を gross に、表示の修正(`rcore/position-fixes`)。

## 3. 入金を確定とみなす基準(merchant・取引所向け)

- **使ってはいけない基準:** block の数、blue score の深さ、DAA の差、heartbeat の本数。どれも heartbeat で水増しできる。
- **少額の場合:** 自分のノードの selected chain 上で、取引を含む block より blue score が 30 以上高い位置に blue の attempt があり、その後も attempt が続いていること。
- **高額の場合:** 次のどちらかを満たすこと。
  - finality depth 600 blue(約 4 時間)
  - PALW settlement で Final anchor に達している(`getPalwSettlement` / `misaka palw settlement`)
- **heartbeat しか出ていない期間**は確定とみなさない。
