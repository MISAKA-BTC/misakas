2. この経路を、slashだけで閉じることはできない
これは感覚的な限界ではなく、短い証明で示せます。


通常の生成方法を \(H\)、安い生成方法を \(F\) とし、総費用を、

\[
C_H>C_F
\]

とします。


両者が提出するRoot、proof、回答、署名などの公開記録を \(T_H,T_F\) とします。必要なら速い側が待つことで、提出時刻も合わせられるとします。


公開記録が同じ分布なら、

\[
T_H\overset{d}=T_F.
\]

報酬・手数料・slash・担保返却をまとめた純受取額を \(P(T)\) とすると、Nodeが観測する情報が同じなので、

\[
\mathbb E[P(T_H)]
=
\mathbb E[P(T_F)].
\]

したがって利益の差は、

\[
\boxed{
\mathbb E[U_F-U_H]
=
C_H-C_F>0.
}
\]

です。


同じ正しい公開記録を提出できる安い計算方法だけを、公開記録に基づくslashで不利にすることはできません。


この経路を閉じるには、「後から不正と判定する」という方法ではなく、どの生成方法を使っても避けられない計算を、受理条件に結び付ける必要があります。

3. 現FULL1で証明できる防御：全Merkle木の計算は使い回せない
ここが、今回追加した肯定的な結果です。


現VF1では、仕事ごとに、

\[
\xi_j
=
H_{\mathrm{scope}}
(\text{domain}\parallel w_j\parallel \sigma_j)
\]

というscopeを作り、これをすべてのleaf、padding、内部nodeのhash入力へ入れています。


さらに、それぞれの入力に、

leafか内部nodeかという種別
leafの位置
内部nodeの高さと位置
を、一意な符号化で含めます。


仕事 \(j\) の全レコード数を \(D_j\)、padding後の葉数を、

\[
L_j=2^{\lceil\log_2D_j\rceil}
\]

とします。


完全二進木の要素数は、

\[
h_j=L_j+(L_j-1)=2L_j-1
\]

です。

定理：異なる仕事に必要なhash計算の下界
古典ランダムオラクルモデルで、既存のMerkle抽出が成功し、scope等の衝突がない事象を考えます。


互いに異なるscopeを持つ \(K\) 件の正しいRootを、初めてTicketに使用するまでに必要な総tree-hash照会数は、

\[
\boxed{
Q_{\mathrm{tree}}
\ge
\sum_{j=1}^{K}(2L_j-1)
}
\]

です。


同じ寸法なら、

\[
\boxed{
Q_{\mathrm{tree}}\ge K(2L-1).
}
\]

証明
第一段階：正しいRootを知るには、木を作るhash照会が必要です。


既存FULL1の抽出議論によれば、正しいRootを初めてTicketに使う時点までに、例外的なhashの一致を除き、そのRootを生成したhash照会が存在します。


第二段階：親を作るには、子のdigestが必要です。


親hashの入力には左右の子digestが含まれます。同じ議論を子へ繰り返すと、leafまで遡れます。


その結果、全leaf、全padding、全内部nodeの入力が、その時点までに照会されている必要があります。


第三段階：同じ木の中で、hash入力は重複しません。


種別、位置、高さを含むため、木の各要素に対するhash入力は異なります。一つの木には \(2L_j-1\) 個あります。


第四段階：別の仕事とも重複しません。


別仕事はscopeが異なり、scopeが全hash入力に含まれるため、別仕事の照会集合とも交わりません。


したがって、必要な異なる照会数を合計すると、

\[
Q_{\mathrm{tree}}
\ge
\sum_j(2L_j-1)
\]

になります。□

この定理が閉じる経路
行列計算を安く済ませても、別仕事の正しいRootを作るための全tree-hash計算は省略できません。


零入力の専用生成器を使っても、過去のprefixから再構成しても、この下界は変わりません。


現在の通常の木生成器は、一件につき \(2L-1\) 回のtree hashを行います。相手にも同数以上が必要なので、

tree-hash照会数という尺度では、通常生成器より少ない仕事で、別仕事の正しいRootを作る経路を排除できます。

これは、今回の要求に対して示せる具体的な費用保証です。

限定も明確にします
この \(Q_{\mathrm{tree}}\) は、外注・協力者・利用した既存計算を含む総生成照会数です。Rootを第三者から受け取ったMiner本人が、同数を自分で計算したとは言えません。


また、これは古典ランダムオラクルへの照会数の下界です。具体的なSHA-256の衝突困難性だけから、同じGPU時間や電力の下界まで得られるわけではありません。


そして、強制されているのは、traceをcommitするためのhash計算です。通常のLLM算術を毎回同じ手順で実行させたという保証ではありません。

4. 既存の \(bC\ge KN\) から、安価化の限界をさらに明確にできる
既存FULL1では、明示した計算モデルと例外事象の条件下で、

\[
C_{\mathrm{fast}}(K)\ge\frac{KN}{b}
\]

という下界があります。


これだけでは、通常実装との差がどれほどあるのか分かりません。


そこで、同じ計算モデルで通常生成器の上界も示します。

\[
C_{\mathrm{normal}}(K)\le\alpha KN.
\]

両方を組み合わせれば、

\[
\boxed{
\frac{C_{\mathrm{normal}}(K)}
     {C_{\mathrm{fast}}(K)}
\le\alpha b
}
\]

です。


これにより、

入力規模や候補数が増えるほど、計算共有によって際限なく有利になる経路を、定義したモデル内で制限する

ことができます。


ただし、\(\alpha b\) が大きければ大きな定数倍の高速化は残ります。通常と同額以上を意味する \(\alpha b=1\) は示していません。

今回、通常生成器の上界も具体化した
masked \(A,B\) を先に計算し、出力補正を整理した生成器では、有限体の加減乗算回数は、

\[
\begin{aligned}
A_{\mathrm{normal}}
={}&2N+4nd+4dm+2d+4nm+2m\\
\le{}&18N
\end{aligned}
\]

です。


これは実装したカウンタでも確認しました。


ただし、\(\alpha=18\) としてよいわけではありません。 この18には、hash、メモリ読み書き、符号化、制御などが入っていません。通常実装との総費用比を証明するには、それらも同じ機械モデルで計上する必要があります。


また、word生成量の下界とhash照会数の下界は、操作の重なりを確認せず単純に足し合わせません。

5. 「証明を重くして、安い方法の利得をなくす」は解決にならない
前のご提案に対して、ここも数式で確認しました。


一候補を作る費用を \(C_H,C_F\)、当選確率を \(p\)、当選後に課す共通proof費用を \(P\) とします。


独立試行・一定候補費用というモデルでは、当選一件あたりの期待費用は、

\[
W_H=\frac{C_H}{p}+P,
\qquad
W_F=\frac{C_F}{p}+P.
\]

したがって、

\[
\boxed{
W_H-W_F=\frac{C_H-C_F}{p}.
}
\]

共通のproof費用は相殺され、費用差は残ります。


大きな \(P\) によって比率を1へ近づけることはできます。しかし、全員の採掘費用を大きくして差を薄めているので、証明生成の採算問題を悪化させます。


さらに、標準proverの費用を測っただけでは、最適化されたproverにも同じ費用が必要だとは言えません。Groth16の原論文が示すprover処理量も、その構成のアルゴリズム費用であり、あらゆる生成方法の実費下界ではありません。


したがって、proof生成を意図的に重くすることを、安価な正当計算への主要な対策にはしません。

あなたが維持したいのが、

「hashを大量に行うから費用が掛かる」ではなく、
「LLM内部の計算を省略できないから費用が掛かる」

という条件なら、現rank-1 FULL1の証明だけでは足りません。


必要なのは、新しいkernelについて、

\[

]
\]

を、cache、前処理、batch、特殊モデル、共有計算を許した最良の生成方法に対して上から抑える定理です。


rank-\(r\) のnoiseとblock-prefixを使う行列積PoUW研究は、この方向を扱っています。ただし、相関した中間値の生成について明示的な困難性仮定を置いており、PALWの現在のrank-1構成へそのまま適用できる完成証明ではありません。また、その論文自身が、設定によっては高速行列積でnaiveな \(n^3\) より少ない時間で全中間値を生成できることを示しています。
