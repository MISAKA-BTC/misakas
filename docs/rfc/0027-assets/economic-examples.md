# RFC-0027 — 資金フローと資本感度の説明例

**すべて合成の数式例であり、採択された料金、実測費用、Miner収益、heartbeat予測ではない。** [RFC本文](../0027-miner-account-bond-and-panel-incentives.md) / [ADR](../../adr/0193-miner-account-bond-for-panel-incentives.md)。

## 1. 責任は最低額に内包する

最低100,000 MSK、1 claimの新責任を仮に12,000 MSKとする。

| claim残存数 | 責任総額 | 必要Account Bond | 最低額を超える分 |
| ---: | ---: | ---: | ---: |
| 1 | 12,000 | 100,000 | 0 |
| 5 | 60,000 | 100,000 | 0 |
| 8 | 96,000 | 100,000 | 0 |
| 9 | 108,000 | 108,000 | 8,000 |
| 20 | 240,000 | 240,000 | 140,000 |

同じaccount10万で20件それぞれ12,000の全額を約束してはいけない。20件を保証するなら240,000を拘束する。1件の違反で100,000を取ると約束したわけでもない。その約束には当該責任への100,000の予約が必要になる。

## 2. 不正が確定した場合の資金の動き

初期資金はMiner account 100,000、requester 6,000。Panelは0、未使用FeeEscrowは0とする。requesterが6,000を前払いし、適格に完了した作業へ4,000を払い、2,000は未使用となる。

Minerの不正確定後、新accountから合計12,000を徴収する。このうち4,000を実費負担者へ償還し、2,000をPanelの固定bounty、6,000をburnにする。未使用FeeEscrow 2,000はrequesterへ返す。

| 勘定 | 初期 | 決着・未使用額返還後 |
| --- | ---: | ---: |
| Miner Account Bond | 100,000 | 88,000 |
| requester | 6,000 | 6,000 |
| Panel | 0 | 6,000 |
| 未使用FeeEscrow | 0 | 0 |
| burn累計 | 0 | 6,000 |
| **合計（burn込み）** | **106,000** | **106,000** |

Panelの6,000は作業料4,000 + 成果報酬2,000。償還された4,000はPanelへの二度目の支払ではない。Minerは最低額を割るので、新規claimを停止して補充を要するが、既存応答・回復は継続できる。

全役割を同じ攻撃者が持っていても、その主体に残るのは100,000であり、初期106,000から6,000を失う。これはこの閉じた資金フローでの還流検算であって、計算省略・外部利得・他の補助まで含む全攻撃の抑止証明ではない。

## 3. 正しいclaimだった場合

同じ4,000の適格作業を行い、申立てを棄却した場合、新accountは100,000のまま。Panelは作業料4,000を受け取り、requesterには未使用2,000だけが返る。合計は106,000で、新accountの没収はない。

従って「不正を出さないとPanelが無収入」ではなく、完了作業の料金と立証成功の上乗せを区別できる。ただし誰が初期費用を拠出するか、支払成熟の待ち時間と費用立替がどれだけ必要かは別の実用性課題である。仕事・受領資格・料金の適格性は合意規則で確認する必要がある。

## 4. 長く保持すると資本は増える

ここでは責任保持を**仮に2日**、新責任を12,000/claim、旧予約を説明上3,000/claim、旧利用率を0.5とする。2日は実装済みhorizonでも推奨の責任期間でもない。定常状態で `残存件数 = 1日件数 × 2` とした単純例である。

| 仮のclaim/日 | 仮の残存件数 | 新account | 旧予約を支えるP | 二勘定合計 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 2 | 100,000 | 12,000 | 112,000 |
| 5 | 10 | 120,000 | 60,000 | 180,000 |
| 10 | 20 | 240,000 | 120,000 | 360,000 |
| 30 | 60 | 720,000 | 360,000 | 1,080,000 |

他の下限、Q/B/R/F、資源予約、fee、post-Finalの実際の責任、他役割の担保は含めていない。最初の行が既存登録下限を満たすとは保証しない。新account10万だけで30 claim/日を維持できるという設計ではないことを示すための例である。

この仮定では10万に8件まで新責任を入れられ、2日保持なら平均4 claim/日がその勘定だけの上限になる。実際のprofileの全分岐費用と責任期間を測り、これで必要なREAL cadenceを維持できないなら未達と報告する。heartbeat率の測定をこの算術から作り出さない。

## 5. 再現方法と限界

```sh
python3 docs/rfc/0027-assets/reproduce_examples.py \
  --json-out /tmp/rfc0027-examples-results.json
```

[実行結果](examples-results.json) / [スクリプト](reproduce_examples.py)。16件の検算は、最低額/責任境界、重複と別root、原子的失敗、全件徴収、他予約保護、既存利用率、累積償還、資金保存、自己還流、整数不正を扱う。

この小さな例は署名、共有frontierの全実分岐、F02供給、包含、deadline、post-Final、実ノードの状態root、支払成熟、reorg/IBD、実際の費用・参加率・heartbeatを実装していない。AB01–AB16や経済gateを実装済み・合格にしない。
