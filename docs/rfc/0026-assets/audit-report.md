# RFC全件整合性監査 — オンチェーン対話・応答期限・客観的default

**作成日:** 2026-10-19（Asia/Tokyo）  
**対象:** 添付 `misakas-pre (1)(1).zip` の `docs/rfc/RFC-0001〜0025`  
**対象ZIP SHA-256:** `367c7bd16c9136fe434eacd2ae70c59dd2a63b5a5ce865f431b9347412288583`  
**性質:** 文書整合性の静的監査。採択・実装・有効化の承認ではない。

## 1. 総合判定

**オンチェーンで義務と手番を確定し、責任者の署名を検証し、局所再計算または適格な応答義務違反から裁定する、という骨格は一貫している。** オフチェーン対話やZKへ方針を戻す必要は、この監査からは導かれない。

ただし、**「DDoSを排除したので、応答が収録されなければ安全にslashできる」という完成状態にはない。** 収録可能性と外部検証者の資源アクセスには、RFC自身が未確定と認める条件が残る。加えて、採用済みの3,120／10,000方針と、Draftの3,200／混雑延長方針、既存署名方式と64 KiB目標、remote minerと対話署名の責任分担に、統合時に解消すべき不整合・条件付き非両立がある。

**判定を分けると、方向性は整合、統合仕様の閉鎖は未完、実装・有効化の安全性は本監査では未実証。**

本書の11項目は「11件の稼働中の脆弱性」という意味ではない。2項目は有効化前に閉じるべき設計条件、7項目は契約・資源・経路・統合に関する要修正事項、2項目は境界・文書管理の要整理事項である。Draftが未完成であること自体を欠陥とは数えず、現在の方針を同時に実装するときに判断が分かれる箇所、または保証に不可欠な未決条件を挙げた。

## 2. 対象と方法

番号付きRFC **25件・19,649行・1,831,970 bytes** を対象に全文横断照合を行い、現行の規範節、末尾改定、採用／撤回／移行の注記を重点読解した。README・番号順INDEX・TOPICSも照合した。RFCごとの確認範囲は [coverage.md](coverage.md) に記載する。

PRINCIPLES、設計凍結規程、参照されたSpec・統合記録、署名・裁定・期限・分岐数に関するコードを補助的に照合した。大きなRFC内の全履歴ログ・全fixtureの個別正当性、全Rustコードの逐語監査、暗号実装の監査は範囲外である。

根拠は今回のZIPに限定する。以前の会話での説明や、旧ZIPの監査結果だけから現行実装を断定しない。ZIP内のフォルダ名が `pre` でも、稼働中t12のbinary・現在のbranch先端と同一であるとは認定していない。

各根拠は [source-evidence.md](source-evidence.md) に原本のパス・行番号・SHA-256付きで収録した。算術と参照の存在確認は [reproduce_checks.py](reproduce_checks.py) / [checks.json](checks.json) で再現できる。**12件のチェックは静的な算術・ソースマーカー確認であり、プロトコルの12件の実ノード試験ではない。**

## 4. 詳細な指摘

<a id="f01"></a>
### F01 — 期限の数値だけでなく、「どの時計か」を統一する必要がある

**原文。** RFC-0014の2026-10-19改定は、通常の異議受付をoriginal acceptanceから3,120 DAA、係争の最終期限を同じ起点から10,000 DAAとする。一方、RFC-0025はoriginal acceptanceからcourt全体を通常3,200以内とし、混雑時のE_maxを容量等から導出し、一律10,000で埋めないとしている。RFC-0024付録Cには、同時N件の最大doorも3,120以下という受入条件が残る。RFC-0025は0024の全件3,200条件を置換するが、0014の新しい10,000上限との置換表はない。[根拠 F01](source-evidence.md#f01)

**判定。** 3,120と3,200が違うだけで矛盾とはしない。異議受付、訴追完了、性能目標は別の値にできる。また、0014の採用方針と0024／0025のDraftを同格の現行規則とは扱わない。問題は、実装・試験が採るべき最終契約が複数箇所に分散していることである。

**条件付き反例。** RFC-0025の試算条件で、court総量64 KiB×10,000件、court用25,000 B/DAAなら、転送だけで `ceil(655,360,000 / 25,000) = 26,215 DAA` が必要になる。これと「その全件をoriginal+10,000以内」を同時には満たせない。実測ではなく、原文の仮定を使った容量下限である。

**最小の修正。** 現在のユーザー方針を基準に、通常の申立て締切と10,000のhard deadlineを主契約にし、3,200は対象profileを限定した性能目標などへ明示的に位置づける。混雑延長はhard deadline内の予約調整なのか、それを超える別の将来方針なのかを決める。10,000を維持するなら、受理前のoriginal claim容量制限と帯域・CPU予算で収まる負荷だけを引き受ける。受け付けた後に正当なcourtだけを捨てて帳尻を合わせない。

**閉鎖試験。** 異議が通常受付窓の最後に届き、Minerが毎回合法的な最遅応答を行い、最後の証拠・収録・回復も必要になるケースについて、残余予算を機械的に検査する。`10,000−3,120=6,880` は予算差であり、最後の受理可能位置には等号・排他的境界の余裕を別途入れる。

<a id="f02"></a>
### F02 — 「提出機会の保証」と「容量の予約」は別の規則である

**原文。** RFC-0014 Eは正規の提出機会がないMinerを単なる期限切れでslashしないと定め、同時にローカルなDDoS申告だけで延長しないとする。同節は、chain上の無応答だけではネットワーク障害と応答拒否を区別できないことも認める。RFC-0025 §5.5は、ローカルmempoolにしかないtxの非収録をblock-invalidの根拠にしてはならず、容量隔離とbase-chain inclusionの仮定を分けるとしている。[根拠 F02](source-evidence.md#f02)

**重要な反例。** 次の二つは同じオンチェーン履歴になり得る。

- 履歴A：Minerが応答を作らず、期限まで有効応答が収録されない。
- 履歴B：Minerは有効応答を署名・送信したが、配送または収録が妨げられ、期限まで収録されない。

オンチェーンの不在だけから、Aだけを処罰しBだけを救済する判定は作れない。署名は発言の帰属を認証するが、未収録の送信・受信時刻を自動的に認証するものではない。

**判定。** 「オンチェーン対話＋期限違反へのdefault」は筋が通る。しかし、「DDoSをなくしたので無条件に安全」という強い読み方は原文の保証範囲を越える。各ノードが同じように評価できる予約・手番・期限の述語と、配送・正直な収録主体について参加者が引き受ける環境前提の切り分けが未完である。

**最小の修正。** 少なくとも以下を単一の規範へ置く。

1. acceptedな義務、応答権限、必要bytes/work、予約、deadline、適格応答の完了条件。
2. 「予定された正規の処理機会」の具体的な計算と、合意で観測できるservice違反の定義。
3. 合意で観測できない個別の通信妨害を、どのinclusion／network前提として扱うか。
4. 正常なservice前提での無応答defaultと、前提が崩れた場合の復旧・担保・Finalの扱い。

`service_ok`という名前のフラグを追加するだけでは解決しない。その根拠がローカル回線測定・Panelの申告・mempool観測なら、全ノードで同じ判定にならない。また、有効な応答が来たときだけ時計を進める案では、永久沈黙で時計も止まる。

**DDoS防御の分層。** 受理後の有料court負荷には容量予約と事前費用を使う。一方、受理前の不正codec・重複メッセージ・接続負荷には、boundedな受信queue、長さ検査、署名検証前後のwork上限、peer処理の制限を別に設ける。少額feeを課すだけで後者まで排除したとはしない。これらは設計提案であり、本ZIPの実装保証ではない。

**閉鎖試験。** 予約枠を残した通常tx flood、有料court飽和、署名・codec不正の大量投入、特定Miner応答の遅延、第三者relay、最後の断片欠落を分けて試す。heartbeatでDAAだけが進む条件も必要である。RFC-0008はcourt停止中もclock machineryが進むと定めており、clockの進行自体を応答機会の証明に使えない。

<a id="f03"></a>
### F03 — feeと有限枠だけでは「外部1人の訴追権」を閉じられない

**原文。** RFC-0014 §7.4は、先に開いたcourtによって他者の直接反証や共有progressを排除してはならないとする。RFC-0025 §7は、既存owner上限8とidle回収では全ownerがactiveな共謀を防げず、「外部検証者用1枠」もSybilが取得できると明記する。未証明なら `OneOutsiderCapacityIncomplete` でarming拒否とする。[根拠 F03](source-evidence.md#f03)

**反例となる進行。** 共謀者が全枠を占有して合法的に応答し続ける。外部の正直な検証者は具体的な不一致を把握しているが、完成した直接証拠にはまだ追加開示が必要である。このとき「完成済みdirect proofは受理する」だけでは、局所化に必要な対話へのアクセスは得られない。

**判定。** これはRFCが自覚している設計未完であり、稼働中の攻撃成立を本監査が実証したものではない。ただし、DDoSを料金で抑止する案を完成扱いするなら最も重要な不足の一つである。

**最小の修正。** original claim受理時に、許容される敵対的分岐を含む責任容量を予約する。争点・root・範囲・手番に対する開示を共用できるようにし、先着アドレスにclaimの排他的所有権を与えない。完成済み直接反証の優先経路と、まだ開示を要する適格訴追の経路を両方示す。どの受付が保証対象で、どこからが過負荷拒否かを明示する。

**閉鎖試験。** 全枠active、継続的な埋め直し、別site誘導、同じrootの重複申立て、別bondによる再開、低feeで大量の有効noticeを投入する攻撃を使う。「非協力な全員」と「無限の合法入力を有限時間で全処理する」という異なる要求を混ぜない。

<a id="f04"></a>
### F04 — node-lessと、対話中に誰も署名しなくてよいことは同義ではない

**原文。** RFC-0009は計算と署名が終わればMinerがPCを止められる設計目標を置き、providerを鍵・bondの代理人ではなくbyte配信者とする。一方、既存TIRのroot claimと各roundはMinerのclaim bondの鍵による署名を要求する。[根拠 F04](source-evidence.md#f04)

**不足する経路。** Minerが計算済みmaterialをproviderへ置いて停止した後、新しいcourtが始まり、そのsession／round／選択区間についてMinerの署名が必要になった場合、providerはbytesを持つだけではその署名を作れない。第三者relayは作成済みの署名を運べるが、将来の適応的な応答を新しく署名する権限にはならない。

**限定。** すべてのremote経路が失敗すると断定しない。直接の認証済み証拠で終了できるprofile、別のkernel経路、既存のacquitting closeが利用できる場合は分けて検証する。RFC-0009自身も責任移転が完成する前の「PCを切れて無リスク」という約束を禁じている。問題は、node-lessの目標をオンチェーン対話へ一律に適用できる条件が未記述なことである。

**最小の修正。** profile別に「資料提供者」「新しい応答の署名者」「提出relay」「不履行責任者」を明示する。現行署名方式を保つなら、義務が終わるまで利用可能なcourt signerを残す。PC完全停止も維持するなら、限定された応答権限の委任、または第三者が追加署名なしで提出できる認証済み終了証拠の経路を、明示的な別仕様として採択・検証する。資金移動用の鍵をproviderへ渡すことを解決策にしない。

**閉鎖試験。** claim提出直後にMinerとその鍵を停止させ、後から新しいsessionを開始し、複数の分岐を選んでも必要な有効応答が作れるかを、資料取得成功と分けて試す。

<a id="f05"></a>
### F05 — 64 KiBは現行対話の単純なパラメーター変更では達成できない

**原文。** RFC-0014の3／5往復は16分岐の仮定例である。ZIP内の `review_heldnode_arity.rs` はshipped t12 presetについて分岐数4を期待する。RFC-0025のSC64は開始からterminalまでの署名・carrier等を含む総量上限候補である。[根拠 F05](source-evidence.md#f05)

tile=16、全履歴について最後まで区間選択を進め、既存の各手番署名を省略しない場合を計算する。

| 条件 | 履歴の最大往復数R | root＋履歴の署名数 `1+2R` | 署名部分だけのbytes |
|---|---:|---:|---:|
| 32K・4分岐 | 6 | 13 | 60,151 B（約58.7 KiB） |
| 2M・4分岐 | 9 | 19 | **87,913 B（約85.9 KiB）** |
| 32K・16分岐の仮定 | 3 | 7 | 32,389 B |
| 2M・16分岐の仮定 | 5 | 11 | 50,897 B |

既存のML-DSA-87署名定数は4,627 Bなので、2M・4分岐では `19×4,627=87,913 > 65,536`。申立て、部分値、operand、opening、最終証拠、外側の追加framingはまだ数えていない。したがってこの条件ではSC64に入らない。

**限定。** これは実proofのbytes測定ではなく、既存形式を維持する場合の下限である。既存テストは今回実行しておらず、稼働中t12の設定も読み取っていない。先読みbundleや新しい署名対象・codecを採用すれば手数とbytesは変わる。また、16分岐なら署名だけが入るという事実は、総量が入る証明ではない。

**最小の修正。** 現行profile、16分岐候補、先読みprofileを別々に名付ける。分岐数、tile幅、context、署名数、各body、最終証拠の最大値を一つのcodec集計にする。既存形式維持を優先するならSC64を未対応目標と明示し、別の上限を承認する。SC64を優先するなら、必要な認証を保つbatch化等の設計変更と全fault routeの上限証明が先である。

**閉鎖試験。** 正直な最遅進行、最終段だけ不正、無応答default、forced disclosureを含めて実際にserializeし、単体courtを成立させる全bytesを合計する。最後の約12 KBやfragment17,408 Bを総量へ流用しない。

<a id="f06"></a>
### F06 — hash-only案は「既存のfoldを削ってよい」という決定ではない

**原文。** RFC-0024 §5.2は数値dissectionに部分値とexact foldが必要とするが、付録C.2は子commitment中心の局所化と最終区間だけの実データ開示を検討する。同付録は、fold検査が必須なら最後へ移せるかを確認するという成立条件を付けている。[根拠 F06](source-evidence.md#f06)

**説明用の反例。** 親の主張が100、正しい二つの子の値が40と50だとする。親と子の値はすべて同じ認証済み構造にcommitされていてよい。子のopeningは正しく、子を個別に再計算しても正しいが、親へのfoldは `40+50=90≠100` で誤る。最終leafだけを調べ、内部の親子関係を一切検査しなければ、この種の誤りを見落とす。

これは実装済みcourtへの攻撃ではない。既存コードは各roundのfoldを検査しており、反例はその検査を不用意に削る案に対するものである。根拠付きhashの一致は、数値関係の成立を意味しない。

**最小の修正。** 本文Bの数値foldを現行規範として維持し、付録Cのhash-only化は未採用の研究・設計候補と明示する。採用する場合は、最終leafの誤りだけでなく、任意の内部parent-child fold不正を局所的に反証できる証拠と、そのrootへの認証を定義する。現在の末端courtが読まない内部関係を、最終leafへの言い換えだけで消さない。

**閉鎖試験。** 親だけ不正、子だけ不正、複数の子で相殺、Sum／Max、root totals依存のsoftmax、HistTileコピー不一致、すべてのopeningは有効というケースを追加する。新方式の完結性が示されるまで、軽いhash比較をexact courtと同等と扱わない。

<a id="f07"></a>
### F07 — 延長は、すべての署名済み依存契約の内側でなければならない

**原文。** RFC-0008 R8-WINDOWは、native紛争期限の延長が依存pathの最短の署名済みhorizonを越えてはならず、既存termsを越える場合は新しい署名と資金を要するとする。RFC-0014は有効な申立てで関連期限を一括延長する。RFC-0025 §6には、最大延長を最初のtermsへ含め、署名済み元frameを壊さずeffective termsを導出する方策がある。[根拠 F07](source-evidence.md#f07)

**反例となる組合せ。** original courtはa+10,000まで延長できるが、依存workerまたはproviderの有効な署名契約がa+6,000で終わる場合、a+9,000の回答を無条件に要求すれば旧契約を越える。一方、既存horizonに従えばcourtの延長保証を満たさない。申立て後に被告の追加同意を必須にすると、被告が延長を拒否できてしまう。

**判定。** 解決方向は0025に既に書かれている。ただし、0014・EXEC依存・provider lease・kernel liability・post-Finalの各時計へどう適用するかが未統合である。単一claimのfieldだけを変える実装は不十分。

**最小の修正。** new original acceptance時に、最大10,000の係争と必要な後続責任を全依存契約が既に覆うことを検査する。通常の延長時に新しい被告同意を取り直さなくてよい上限を、最初から署名・担保・資金に含める。旧claimは旧rulesetを維持する。

**担保解放の注意。** 発行枠の `d+W`、申立て窓、court期限、経済Final、Gate C、支払・retentionは別である。RFC-0018にはFinalから始まる公開告発windowがあり、RFC-0008のmonetary materialは最後の実支払＋W_matまで保持する。したがって「何もなければ3,120でbond全額を必ず返す」「courtを10,000で終えたら即全削除」は、既存の責任条件を省略した読み方になる。0014自身も他の保持・責任条件を満たすことを要求しており、ここは無条件返還との矛盾ではなく、その限定を実装へ徹底する必要がある。

**閉鎖試験。** native→EXEC→kernel→providerの依存鎖、最短lease、後払い、複数claimが同じbondを参照、Final後のconviction、再起動・reorg時のeffective terms復元を組み合わせる。

<a id="f08"></a>
### F08 — 全体時計は進むが、係争とfrontierがどの状態で終わるかを明示する必要がある

**原文。** RFC-0023段階1は共有frontierを残したまま未解決claimの遅れにL_class上限を置く。段階2の独立claim進行は別fenceで未完である。RFC-0006はopenなDA／court中の中立終了とFinalを抑止する。RFC-0025はservice envelope崩壊時にFinal保留・復旧へ移り、E_max到達だけで未解決不正を無罪／Finalにしてはならないとする。[根拠 F08](source-evidence.md#f08)

**残る状態。** hard deadlineへ到達したが、正規の処理機会が成立せず参加者defaultにもできない場合、担保と証拠を保持すること自体は安全側である。しかし、それが共有frontierのblockingな未解決集合に残り続けるのか、どの規則で非creditの終端へ移るのかが必要になる。clockや通常取引が進むことは、settlement frontierも有限時間で進むことを意味しない。

**限定。** service障害を保証対象外と明示すれば、「障害中も必ずL_class以内」という論理矛盾を要求する必要はない。RFC-0023自身もネットワーク停止中の前進は保証しない。本指摘は、service failure、全体hard deadline、共有frontier、保留責任の境界を同じ状態遷移表に接続できていないことを指す。

**最小の修正。** 各終了理由について、claimのcredit、courtの終了／復旧、担保、証拠、共有frontier、pruningへの効果を別fieldで明示する。単に未解決を「解決済み」に変更したり、期限だけで有効なFinalにしたりしない。段階2が未有効なら、その独立進行を段階1の可用性保証へ借用しない。

**閉鎖試験。** 係争を伴う最古claim Aと無関係な正直claim Bを用意し、Aの期限・service失敗・復旧・late convictionで、BのFinal、Gate C、報酬出力、settled、safe frontier、pruningを別々に記録する。

<a id="f09"></a>
### F09 — 等号の扱いは、変数ごとに定義しなければならない

**原文。** RFC-0014の10-12改定は `d <= deadline`／`d > deadline` のように境界を一意にする例を記す。RFC-0024／0025はpublic convictionのcollect_untilを排他的境界とし、既存foldも `daa >= collect_until` を拒否する。RFC-0019では受理DAAはmerged blockのheaderではなくaccepting chain blockのDAAである。[根拠 F09](source-evidence.md#f09)

**判定。** 前者は例示であり、すべてのdeadlineが必ず同じ等号を持つと規定したものではないため、これだけで既存の合意分岐とは判定しない。ただし、同じ「期限」という自然言語で置換すると誤実装しやすい。

**最小の修正。** notice、root、各round、choice、最終fragment、collect、hard deadline、default sweep、refund／bond exitについて、起点・単位・受理区間・等号・同一block処理順・reorg後の再計算を表にする。元headerのDAAを使って締切を迂回しない。

**閉鎖試験。** 各期限の−1／一致／＋1、同一blockで最後のfragmentとdefaultが競合、別順序のmergeset、古いbranchの署名、再起動後のsweepを試す。

<a id="f10"></a>
### F10 — 「別branchにある」と「このsnapshotに統合済み」を分ける必要がある

**原文。** RFC-0014／0024／0025は `palw_court_capacity_v1` を土台にし、0025は `consensus/core/src/palw_court_capacity_v1.rs` を既存の休眠実装と記す。しかし、このZIPに同名ファイルは存在しない。統合残作業表は `integ/g14-court-capacity` / `5b64cac9c` を別branchの作業として記録する。[根拠 F10](source-evidence.md#f10)

**判定。** GitHub全体に実装がないとは言わない。今回のZIPから、その予約scheduler、応答枠、費用、expiryの安全性を検証できないという統合境界の問題である。単なるsession数上限があることと、新しい予約・inclusion機構が統合済みであることを混同しない。

**最小の修正。** 各機能に「設計だけ／別branch実装／統合済み／build済み／敵対的試験済み／有効化済み」を別に付け、commitを固定する。今回のsnapshotを根拠に、DDoS防御または提出保証が実装で閉じたとは記載しない。

**閉鎖試験。** 実際に統合されたソースで、admission、codec、fold、scheduler、料金、deadline sweep、snapshot／IBDまで一貫した呼出経路を確認し、出荷binaryで負荷と復旧を測る。

<a id="f11"></a>
### F11 — 置換関係を文書末尾の自然言語だけに依存させない

**原文。** RFC-0021と凍結規程は、合意・責任の意味を変える場合に新RFC／ADRの明示的な採択と置換節を要求する。大きい番号・新しい日付だけで上位にはならない。RFC-0014の方針採用と0025のDraft上位宣言は、正式な規範・旧claim・次fenceへの対応が別途必要である。また番号順INDEXとTOPICSには0024／0025が載っていない。[根拠 F11](source-evidence.md#f11)

**限定。** ユーザーの方針採用を否定したり、Draftが存在するだけで違反としたりしない。状態遷移を変える正式な採択ADRと条項置換の対応を、本snapshotだけでは一意に確認できないという指摘である。

**最小の修正。** 1枚の「current court policy」表を置き、義務・署名・経路・各期限・資源・返還・復旧について、現行規範、採用済み次期方針、未採用案、実装branch、対象fenceを記す。RFC-0014／0024／0025はそれを参照し、旧本文は履歴として残す。INDEX／TOPICSを更新し、formalなRFC／ADR相互参照と置換節を揃える。

## 5. 矛盾と判定しなかった重要事項

### 5.1 オフチェーンという単語が残っていること

RFC-0006のoff-chain fast pathは資料取得であり、失敗時にオンチェーンの強制開示へ進む。RFC-0014もretrievalとadjudicationを分離する。これは「Panelがオフチェーンで対話を済ませたと申告すればslashできる」方式ではない。資料の事前取得、Panelのローカル検査、rootに認証されたデータのpeer配布は、オンチェーンcourt方針と両立する。[根拠 P02](source-evidence.md#p02)

### 5.2 「無応答でもslashしない」という旧記述

receipt段階で検証者不足・Unavailableから中立に終わる処理と、acceptedなcourtで応答義務者が期限を超える処理は対象が違う。両方が存在してよい。無効な申立てやローカルtimeoutから罰を発生させず、受理済みの具体的な義務についてdefaultを導くことが重要である。[根拠 P01](source-evidence.md#p01) [根拠 P03](source-evidence.md#p03)

### 5.3 Panelを信用しないことと、検証者の承認を使うこと

Panelの申告だけで計算不正を認定しないというcourtの規則と、Gate Cが明示的な正直割合の前提の下で抽選検証者の承認を使うことは役割が違う。署名は当事者と対象を認証し、計算不正はexact courtで確定する。この役割分離はPRINCIPLESと整合する。[根拠 P01](source-evidence.md#p01) [根拠 F07](source-evidence.md#f07)

### 5.4 モデル審査廃止と、資源上限付きclass admission

公開状況・保持者数・取得可能性をチェーンで審査しないことと、受理するclassの演算・形状がcourt上限を満たすか決定論的に検査することは別である。モデル階層の1.0／0.3、登録不変性、claimごとの検証は両立する。[根拠 P04](source-evidence.md#p04)

### 5.5 旧VM・Panel=0・メディア改善案

撤回または当面延期の明記があるものを、現行オンチェーン方針の矛盾として数えていない。Panel=0は将来の別gateであり、当面Panel=1を維持する改定がある。画像・動画・モデル改善の延期は共有TIR／テキストcourtの無効化を意味しない。[根拠 P05](source-evidence.md#p05)

### 5.6 checkpointの10,000とbond／証拠の10,000

RFC-0025はこれらを明確に分離している。周期的checkpointを作っても、未解決のcourt、延長記録、lease、再取得・復旧に必要な証拠は保持する。rootの一致だけを状態遷移の正当性の証明にしないことも明記されている。この方向は一貫している。[根拠 P06](source-evidence.md#p06)

## 6. 方針を変えずに一本化するための仕様案

以下は**監査上の修正提案**であり、実装済み規則でも新しい採択の宣言でもない。

| 層 | 一本化すべき契約 |
|---|---|
| 基本経路 | 受理済みsessionのroot／開示／選択／終端をオンチェーンで扱う。直接反証可能なleafは既存の直接経路も残す |
| 発言の帰属 | Miner応答、challenger選択をそれぞれ責任鍵で認証。session、round、scope、root、rulesetにbind。relayは署名者と区別 |
| 通常窓 | original acceptanceをaとして申立て締切をa+3,120とする方針を主契約へ明示。等号は変数別に固定 |
| 全体期限 | 受理する対象負荷では、係争をoriginal acceptanceのaから10,000以内に完結させる。申立てごとに時計をresetしない |
| 各手番 | 相手が回答可能な最大bytes/work・収録余裕を持つ期限。最終証拠・回復の残余予算を予約し、終盤のclampで時間を奪わない |
| 事前予約 | original受理時に、全対象claimが同時に争われる範囲の資源・料金・担保・保持を確保。将来の単なる期待収益は保証にしない |
| 通常混雑 | 合意予約から調整するが、主契約のhard capと既存予約を維持。入りきらない新しい経済的責任の受付を抑制 |
| 非応答の判定 | 正式な義務・手番・適格応答不在・期限超過に、明示したservice/inclusion条件を結び付ける。計算不正とは別のdefault |
| 環境前提外の障害 | ローカル申告を合意事実にせず、定義可能な障害と復旧・責任保持を明記。無条件の有限返還や不当slashゼロを保証しない |
| 終端の勝敗 | 算術不正はMiner側、正規の開示不履行はその責任者、Minerが義務を果たしたのにPanelが完成できなければPanel側の敗訴処理 |
| 複数の責任 | claim、EXEC依存、provider、post-Final、Gate C、既払・未払費用、retentionの最大必要期間を同時に満たす |
| 有効化 | 上記の条項対応、実装、出荷binaryでの実測、敵対的試験、移行・復旧の記録が揃うまで休眠 |

「全体期限」の行の `a` はoriginal acceptanceの絶対DAAであり、目標は `a+10,000`。clockの受理起点を後ろへ移して達成表示しない。現在の3,200最適化とSC64は、この主契約から切り離した、profile別に採択・測定する性能目標として扱うのが最小の整理である。

| T04 | 正常tx flood／大量の有料court／不正codec flood | 予約・受信・parse・署名検証の各資源を分けて測定。合法応答が所定の遅延内 |
| T05 | 全owner枠を共謀者がactiveに占有 | 外部1人が、未完成の局所化段階から訴追できる。完成済み証拠の入口だけでは合格にしない |

## 8. 修正・確認の順序

最初に **F01・F02・F03** を閉じる。すなわち、期限の主契約、どの条件で無応答に帰責できるか、正当な参加者が枠を失わない予約・受付の規則を決める。ここが曖昧なまま応答feeやdeadlineの数値だけを変更しても、安全なtimeout処理にはならない。

次に **F04・F07・F08** で、実際に署名する主体、依存責任、障害時の終端とfrontierを接続する。**F05・F06** の証拠小型化は、これらの責任・正当性を保った上で行う。

最後に **F09・F10・F11** の境界、統合ソース、置換・fence対応を固定し、同じ出荷binaryで受入試験を行う。設計メモ・別branchのコード・toy testを混ぜて「すべて完了」と表示しない。

## 9. 実施したこと／していないこと

**実施:** 添付のRFC全25件を対象とした全文横断照合、現行規範と改定の重点読解、上位原則と関連仕様の照合、選択したコードの静的確認、全件一覧・根拠抜粋・条件付き算術の作成。12件の算術・ソースマーカー確認に合格。

**未実施:** 全Rustコードの監査、暗号実装監査、cargo build/test、実モデルcourt、ネットワーク負荷試験、DDoS／検閲耐性の実証、t12 binary／live設定の確認、fence変更、RFCへの追記、Git commit／push。

**最終判断:** 方針の骨格は維持できる。ただし、オンチェーンに置いたことだけでは提出機会は保証されず、料金を取ることだけではDDoSは排除されない。必要なのは、認証された義務、有限の資源予約、明示的な収録前提、役割別のdefault、署名済みの責任期間、復旧までが一つの規範で整合することである。
