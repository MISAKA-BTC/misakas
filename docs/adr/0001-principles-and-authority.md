# ADR-0001 — 設計原則・暗号基盤・権限境界を選ぶ理由

- 文書日付：2026-11-26（Asia/Tokyo）
- 文書区分：**DECISION_RATIONALE**。判断の背景・理由・代替案・帰結を記す。
- 対応仕様：[RFC-0001](../rfc/0001-principles-and-governance.md)。数式、形式、状態遷移、受入条件と提案部分の区分はRFCを正本とする。
- 進捗・実装完了・公開有効化を示す文書ではない。新たな採否は明示的な決定を必要とする。

## 背景

MISAKAは独立したネットワークであり、実行の正しさ、採掘費用、台帳上の合意、モデルを利用する認可を別々に扱う必要がある。これらを同じ「承認」へまとめると、モデル管理者の判断が台帳確定や個別計算の正当性へ広がってしまう。

## 決定

ネットワークidentityと暗号の用途を固定し、計算の検証・モデル認可・台帳合意の権限を分離する。LLM計算の暗号学的validity proofは採用せず、再実行、公開資料、局所裁定と経済的責任を使う。暗号方式、型、署名domain、供給上限の仕様は対応RFCに置く。

## 判断理由

- Nodeが全モデルを保有しなくても客観的な争点を裁ける構成と、検査を実行する参加者の条件を明確にするため。
- BFTの採用票を「この推論が正しい」「この費用を負担した」という証拠へ拡張しないため。
- 旧ネットワークと新ネットワーク、署名domain、hash幅を混同した誤受理を防ぐため。
- 正しい高速実装と、計算結果の偽造を区別するため。

## 比較した方針

| 方針 | 判断理由 |
| --- | --- |
| モデル管理BFTが台帳finalityも決定する | 認可権限がfork choiceへ拡張するため採らない |
| 暗号学的計算証明へ検証責任を置き換える | ユーザーが定めたMISAKAの検証方針の対象外 |
| hashや署名の一致を全計算の正しさと呼ぶ | 認証する性質が異なるため採らない |
| 明示的な故障前提を持つ役割分担 | 採用。保証範囲を個別に評価できる |

## 帰結

正直割合、資料取得、包含機会、検証能力を明示する必要がある。局所計算検査の成立だけで、PoW費用やDAG安全性まで証明されたとは扱えない。基盤暗号の変更もモデル採用とは別の互換移行を要する。
