# ADR-0018 — 有界保存・pruning・IBDを選ぶ理由

- 文書日付：2026-11-26（Asia/Tokyo）
- 文書区分：**DECISION_RATIONALE**。判断の背景・理由・代替案・帰結を記す。
- 対応仕様：[RFC-0018](../rfc/0018-storage-pruning-and-ibd.md)。数式、形式、状態遷移、受入条件と提案部分の区分はRFCを正本とする。
- 進捗・実装完了・公開有効化を示す文書ではない。新たな採否は明示的な決定を必要とする。

## 背景

全状態の繰り返しコピーや無制限snapshotは、ローカルdevnetでも保存容量を急増させる。ただし、容量不足だけを理由に資料を消すと、未解決責任や再起動・reorgの検証が失われる。

## 決定

保持義務からlive setを導き、有界な世代管理、差分、圧縮、pruning、IBD streamを使う。既存rootを保つ最適化と、新しい認証state mapの提案を分離する。データ構造、pin、stream検査、GC、rootの式はRFCに置く。

## 判断理由

- 必要な責任を保持したまま、不要な複製やcacheを回収できるため。
- local資源不足をpeer不正やblock無効へ誤分類しないため。
- 不完全なimportや異なる親rootの行を、起動状態へ昇格させないため。

## 比較した方針

新認証state mapの候補では、範囲完全性と更新・深さの上界を同時に扱える順序保持trieを提案する。hash順だけの配置は必要なprefix範囲を直接表せず、全整列葉の更新は高価、履歴依存の木形は同じ状態の同一性を扱いにくい。これらの比較理由をここへ置き、具体形式はRFCの提案節に置く。

## 帰結

新root形式は提案のままで、文書整理では採択しない。未知の行を不在と扱わず、署名・曝露journalは通常のchain undoと別に保つ。一定disk容量を主張するには負荷・保持期間・一時領域の条件が必要である。
