# ADR-0019 — クライアント・RPC・原因保持を選ぶ理由

- 文書日付：2026-11-26（Asia/Tokyo）
- 文書区分：**DECISION_RATIONALE**。判断の背景・理由・代替案・帰結を記す。
- 対応仕様：[RFC-0019](../rfc/0019-clients-rpc-and-diagnostics.md)。数式、形式、状態遷移、受入条件と提案部分の区分はRFCを正本とする。
- 進捗・実装完了・公開有効化を示す文書ではない。新たな採否は明示的な決定を必要とする。

## 背景

異なる拒否を同じエラーへ潰すと、待てば進む状態、修正が必要な不整合、運用者が判断すべき停止を区別できない。再送や3ピア観測も、成功段階を混同すると誤った進捗になる。

## 決定

型付きの原因連鎖とclaim単位の段階診断を使い、その原因から再試行条件を決める。署名済み提出物と観測根拠を保持し、RPC・SDK・Studioはnativeの正規判定を共有する。型、field、状態、再送・復旧契約はRFCに記す。

## 判断理由

- 文字列一致への依存と、同じ原因の無意味な再試行を減らすため。
- 資金不足、quote不一致、資料欠落、型不一致などを正確に説明するため。
- 取引IDだけを保存して再送できなくなる復旧不備を避けるため。
- 秘密を開示せず、選択親と根拠recordから診断可能にするため。

## 比較した方針

一つのUnknownエラー、失敗を捨てるfilter_map、RPC成功を確定決済とする表示、未登録とAPI非対応を同じ空応答へする方式は採らない。エラーを細分化するだけでなく、運用上の次の行動へ結び付ける。

## 帰結

公開APIの互換性と、内部原因の詳細保持を分ける必要がある。診断ログ自体も有界にし、鍵・秘密share・認証tokenを含めない。
