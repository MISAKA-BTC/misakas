# ADR-0020 — devnet・公開有効化・文書管理を選ぶ理由

- 文書日付：2026-11-26（Asia/Tokyo）
- 文書区分：**DECISION_RATIONALE**。判断の背景・理由・代替案・帰結を記す。
- 対応仕様：[RFC-0020](../rfc/0020-devnet-release-and-migration.md)。数式、形式、状態遷移、受入条件と提案部分の区分はRFCを正本とする。
- 進捗・実装完了・公開有効化を示す文書ではない。新たな採否は明示的な決定を必要とする。

## 背景

部品試験だけを繰り返しても、実LLM由来のclaimが受賞・決済までつながるとは限らない。毎回の長時間待機、台帳の複製、旧仕様の積み重ねも、開発の原因特定を遅らせる。

## 決定

ローカルdevnetで通常経路を受賞・決済まで接続し、関連する短時間試験の後にFullを行う。文書はRFCを実装仕様、ADRを判断理由として、それぞれ現行テーマへ統合する。試験手順・有効化・番号・移行・削除規則はRFCを正本とする。

## 判断理由

- VPSへ配備する前に、不具合を再現・修正できるようにするため。
- 待機を実装作業の代替にせず、同じclaimやcheckpointから目的の遷移を検査するため。
- 文書数と重複を減らし、現在のルールとその理由を迷わず探せるようにするため。
- 古い提案や成功記録を、現在の採択・実装完了へ読み替えないため。

## 比較した方針

旧RFC/ADR本文をarchiveへ積み上げる方式、同じ設計を両方に重複記載する方式、v1/v2別体系は採らない。小さい参照対応表を残し、設計と判断理由は相互リンクする。生の実行証拠は旧設計本文の履歴とは別に扱う。

## 帰結

削除を含む差分適用が必要で、単純なZIP上書きだけでは旧本文が残る。文書番号の整理はwire、署名domain、DB、旧claimの意味を変更しない。公開有効化と本番資産の操作は別工程である。
