### 文書の位置づけ


本書は、RFCが扱う提案・検討と、ADRが扱う意思決定の履歴から分離し、**システムが維持する責務分担、状態境界、不変条件**を定義する。


[PRINCIPLES](../PRINCIPLES.md) と採択済みの変更管理規則を上位の前提とする。既存の採択済み設計と衝突する箇所を、本書の追加によって暗黙に上書きしてはならない。構造変更には既存のRFC・ADR・明示的承認の手続きを適用する。[設計凍結規則](../governance/design-freeze.md) に従い、文書整備と設計変更・有効化を区別する。


本文の **MUST** は必須条件、**MUST NOT** は禁止条件、**SHOULD** は理由を記録した例外が可能な推奨条件を示す。


本文中の概念上のフィールド名・状態名は、既存のRust型、RPC、wire tagが存在することを意味しない。実装時には既存形式との対応表を作成し、必要な変更をversionとactivation fenceで区別する。


### 今回固定するDAGの設計前提


> **モデル＝minerとして、各登録モデルをDAG上の独立した論理的な採掘主体として扱う。各モデルを実行するminer群が、他モデルの実行完了や一括承認を待たず、それぞれの生成条件を満たしたブロックを並列に生成し、同じDAGへ接続できる構造を前提とする。**
>
> **複数モデルの計算結果を単一の生成者に集約して一本ずつブロック化する設計ではなく、DAGの並列な生成・接続・mergeを、モデル単位のブロック生成にも利用する。**


「モデル＝miner」は論理的な生成主体の対応を表す。モデル自体を署名鍵・bond所有者と同一視せず、一モデルにつき一人だけのminerを認める独占的な構造にもしてはならない。実際のexecutor、署名者、bond、報酬帰属は引き続き個別に認証する。詳細は[第8章](#model-parallel-dag)に定める。


### 「証明」の意味


本書でいう証明は、次の三つを区別する。


| 種別 | 証明・認証できること | 証明しないこと |
|---|---|---|
| Commitment・署名・Merkle opening | 誰が、どのデータ・実行条件・結果に拘束されたか | 計算全体が正しいこと |
| 検査記録・Panel承認 | 指定された検査と、対象claimへの承認 | 全演算の無条件な正しさ、検証者の物理的なCPU稼働 |
| Courtの客観的証拠 | 認証された局所計算の不一致、二重署名、適格な開示義務違反など | 検査されていない全区間の正しさ |


MISAKAの既存前提に従い、ZK、zk-SNARK/STARK、zkVM、zkML等の暗号学的な計算正当性証明は使用しない。**確率的検査、公開証拠、決定論的Court、担保責任、明示的な正直な検証者の前提**を組み合わせる。Panelの署名を、モデル全体の算術的正しさの証明と呼んではならない。

## 0. ローカルの有用推論と、Miner・Panel・Nodeの責務分離


### 0.1 基本構造


Minerは、MISAKAの登録済み整数kernelと固定された実行仕様に従って、ローカルLLMを実行する。


生成した出力は、対話、コード生成、要約、分析等、利用者が本来必要とする用途に使用できる。マイニング参加のために、同じ推論を証明専用としてもう一度実行することを通常要件にしてはならない。


基本構造は次とする。


```text
利用者
  │ プロンプト・実行条件
  ▼
Miner / Local Runtime
  ├─ 整数kernelによる推論 ────────────► 利用者への実用出力
  │
  └─ 実行記録・commitment・署名
          │
          ▼
     Panel / Evidence Provider
          ├─ 検査
          ├─ 必要な対話
          └─ 検査記録・承認・Court用証拠の構築
                    │
                    ▼
              任意のRelay / Builder
                    │
                    ▼
                   Node
                    └─ 決定論的検証・状態遷移・責任と権利の管理
```


### 0.2 責務


| 主体 | 主な責務 | 通常時に要求しないこと |
|---|---|---|
| Miner / Executor | 推論、実行結果へのcommit、署名、必要な資料の保持・提供 | 推論全体の証明専用再実行、full nodeの運用 |
| Panel / Verifier | 検査、必要な再計算、証拠の組み立て、承認または不正追及 | Minerの資金・秘密鍵の保管 |
| Evidence Provider | 認証可能な資料の保存・配信 | 計算の正しさについての合意上の決定 |
| Relay / Builder | 署名済み提出物の搬送、許可されたブロック構築 | claim所有者や報酬受取先の変更 |
| Node | 署名、状態、予算、期限、Court証拠、権利消費の検証 | モデル全体の保持、全claimのLLM全量再実行 |
| Public Challenger | Panel外からの検査、証拠提出、不正追及 | 特定operatorや既存Panelからの参加許可 |


同じ運用者が複数の役割を実行することは可能だが、**役割の権限・署名・会計・責任は分離する**。同一人物が運用していることをチェーンが完全に識別できるとは仮定しない。


### 0.3 Minerの負担を最小化する原則


Minerの負担は、概念上、次に限定する。


```text
Minerの負担
  = 利用目的の通常推論
  + 実行記録・commitment作成
  + 署名・通信・必要資料の保持
  + 適格な要求があった場合の限定的な追加計算
```


証拠の探索、検査計画の実行、監査用の再計算、Court提出物の組み立ては、原則としてPanelが負担する。


ただし、**「追加の証明計算を通常時に要求しない」と「追加コストがゼロ」は異なる**。ハッシュ計算、記録、保存、通信の費用は残る。その実測値をモデル・実行profileごとに報告する。


Minerへの対話要求は、既存cacheやcheckpointから応答できる形を優先する。追加計算が必要な場合も、要求対象の区間・tile・kernel等に限定する。通常時の都合だけで全推論の再実行を要求してはならない。


### 0.4 出力の利用と認証は分離する


利用者は推論終了後、チェーン上の認証完了を待たずに出力を利用できる。


ただし、UI・APIは以下を分離して表示する。


```text
出力生成済み
claim提出済み
検査中
Final
SecurityCertified
Receipt利用可能
報酬受取可能
```


計算認証は、文章の事実性、有用性、回答品質、業務上の正解を保証しない。


### 0.5 通常対話とAttemptの境界


任意プロンプトのローカル対話を仕事として提出する場合は、free-prompt claimとReceipt系経路を基本とする。


Attempt系では、親、challenge、実行条件等への事前の拘束が必要になる。**終了済みの任意推論を、後から任意のAttemptブロック位置に付け替えてはならない。**


モデル実行の決定性には、整数演算だけでなく、量子化、丸め、overflow、tokenizer、sampling、乱数seed、実行順序、状態更新規則も含める。


### 0.6 モデル単位の並列な生成主体


本章の実行・検査・提出経路は、モデルごとに並列に存在する。モデルAのminer群とモデルBのminer群は、それぞれの計算と生成条件に従ってブロックを生成し、共通DAGへ提出する。


Node、Panel、Relay、Builderを共用しても、共用サービスを全モデルの唯一の生成者・一括承認者にしてはならない。必要な個別の検証、bond予算、成熟条件を維持したまま、モデル間の不要な直列待ちを作らない。

## 1. モデル登録


### 1.1 登録対象


モデル登録は、名前や外部URLの登録ではなく、**不変の実行対象と実行条件の登録**とする。


登録情報は、少なくとも以下を識別できなければならない。


```text
ModelDescriptor
  model_registration_id
  artifact_root
  graph / program identity
  kernel_catalog_version
  arithmetic / quantization specification
  tokenizer identity
  execution / sampling profile
  supported shape and resource bounds
  registrant identity
  applicable policy version
```


実際のフィールド配置とID導出方法は、既存の登録仕様に従う。可変URLは配布先情報であり、モデル同一性の根拠にしない。


### 1.2 不変性


登録後、同じModel IDの重み、graph、量子化規則、意味を変えるkernel仕様を変更してはならない。


変更後のモデルは、新しい登録として扱う。旧モデルのclaim、bond責任、ModelPosition、市場reserve、履歴を、新モデルへ自動的に付け替えてはならない。


モデルの別名や配布URLを変更しても、固定されたartifact rootとの一致確認は維持する。


### 1.3 Permissionless登録とclaim検証の分離


登録には公開された形式・署名・資金・対応実行profile等の決定論的条件を適用する。ただし、これを「モデルが優秀か」「公開されているか」「誰が信用できるか」という裁量的なモデル審査にしてはならない。


既存前提では、genesis・年次フォーク指定モデルは係数1.0、後から登録したモデルは登録時点から0.3とし、モデル単位の審査による自動昇格は行わない。一方、**claim単位の検査と認証は全モデルで維持する**。


以下は別の状態として扱う。


```text
登録情報が受理されている
実行profileが対応されている
そのclaimを裁定できる
そのclaimが認証されている
そのclaimが報酬・合意creditを生む
```


登録受理だけで、未対応演算や未認証claimに報酬・weightを与えてはならない。


### 1.4 モデル配布


モデル本体の配布は、合意プロトコル外の任意の仕組みで行う。


チェーンはモデル全量の配布成功を保証しない。検証者が対象モデルを取得できない場合、その検証能力がないことを明示する。取得できていないモデルを「検証済み」と扱ってはならない。


モデル全量の取得と、特定claimに必要な有限の証拠開示義務は、別の責任として扱う。


### 1.5 対象範囲


本書の初期対象はテキストLLMとする。複数モデル対応を理由に、画像・動画・モデル改善等の延期機能を暗黙に有効化しない。[初期mainnetの対象範囲](../governance/post-mainnet-scope.md) に従う。

## 2. PanelとMinerの対話による検査・Court証拠の作成


### 2.1 通常経路と紛争経路


すべてのclaimでCourtを起動する設計にはしない。


```text
通常経路:
実行 → Commit → 検証対象の決定 → Panel検査 → 承認・所定の状態遷移


紛争経路:
不一致または適格な異議
  → 認証済み資料の取得
  → 対話による局所化
  → bounded exact terminal
  → Nodeによる決定論的裁定
```


通常時の検査記録・承認と、紛争時のCourt証拠は、別の提出物とする。


### 2.2 Commit-before-challenge


Minerは、検証対象が確定する前に、実行条件、入力、出力、実行記録の必要なcommitmentを固定する。


PanelやMinerが、検査結果を見てからclaimの対象、trace、入力、出力を変更してはならない。


検証対象を決める乱数は、適用policyで指定された、commit後の適格なチェーン情報から導出する。MinerやPanelの任意のlocal RNGに置き換えてはならない。


challengeの導出元、導出手順、対象集合、seed、適用policyを、外部検証者が再構成できなければならない。


### 2.3 対話メッセージ


対話メッセージは、概念上、次の情報に拘束する。


```text
claim_id
model / execution profile identity
session_id
round / sequence number
request or response kind
requested range / kernel / tile
previous transcript commitment
payload commitment
applicable deadline
signer and signature
```


この構造により、別claimの回答の流用、過去roundの再利用、応答の順序入れ替え、異なる実行profileへの付け替えを防ぐ。


同じ適格な要求の再送は冪等に扱う。Panelが同じ資料を繰り返し要求してMinerの追加計算を増幅できないよう、要求回数・総bytes・追加計算量に上限を設ける。


### 2.4 証拠構築の分担


**Panelが行うこと：** 検査対象の再計算、commitmentとの照合、不一致区間の探索、証拠の収集、Court提出物の構築と提出。


**Minerが行うこと：** 自身がcommitした結果に関する認証可能な資料の提供、必要な署名、既存資料だけでは応答できない場合の限定的な再計算。


PanelはMiner名義の署名を代行してはならない。資料配信や送信を委託しても、誰の主張であるかという責任境界を変更してはならない。


### 2.5 Courtの局所化


Courtは、大きな実行全体を、そのままNodeに再実行させない。


不一致を区間、step、kernel、tile等へ段階的に局所化し、最終的にNodeが宣言された資源上限内で裁定できる問題へ落とす。


terminal evidenceは、少なくとも以下を結び付ける。


| 要素 | 必須の拘束 |
|---|---|
| 入力・初期状態 | 対象claimの入力と実行条件 |
| 演算 | 登録済みkernelの意味・version |
| 重み・定数 | 登録artifact root |
| 中間値・出力値 | 対象trace・状態commitment |
| 実行位置 | graph、schedule、step・tileの位置 |
| 裁定対象 | 具体的に争われている関係 |


Merkle openingが正しいだけでは、演算が正しいとは判定しない。**データの所属確認と、演算関係の検証の両方**を必要とする。


### 2.6 裁定結果


| 結果 | 意味 |
|---|---|
| Local check passed | 対象となった局所関係が成立した |
| Arithmetic refutation | 認証された値と規定演算の間に不一致がある |
| Material/default violation | 適格な開示・応答義務が期限までに満たされなかった |
| Invalid accusation | 提出証拠や告発条件が成立しない |
| Equivocation | 同一対象に対する両立しない署名済み主張がある |


局所検査の成功を、未検査区間を含む全計算の証明へ拡張しない。


資料不開示を、算術的不正の証明と言い換えない。適用する処分も、違反種別とpolicyに従って分離する。


### 2.7 Panel外からの追及


正しいモデルを保有・取得できたpublic verifierは、公開された参加条件と認証済み資料を用いて、Panelの許可なしに不正追及を開始できなければならない。


Panelが誤って承認した場合や追及を拒否した場合にも、外部からCourtへ到達する経路を維持する。[公開検証設計](../rfc/0015-panel-free-permissionless-verification.md) の、producerの秘密状態に依存しない局所化と客観的裁定の要件を維持する。

## 3. ALW/PALWの三つの機能区分


### 3.1 分類


本書は、ユーザー向けのREAL／Attempt、EXEC／ROUND、Receipt／PFS4を、以下の**論理的な機能区分**として扱う。


既存wire IDや型を、名称の整理だけで同一視・再解釈してはならない。


| 区分 | 役割 | 計算権・creditの扱い |
|---|---|---|
| **REAL / Attempt** | 新しい計算結果を、規定の生成条件に従って提出する | 新規の計算提出系として維持する |
| **EXEC / ROUND** | 分割された計算、資料、検査、実行進捗、Court対話を搬送する | 搬送した事実だけで新しい計算権を作らない |
| **Receipt / PFS4** | 過去に認証・成熟した計算権を消費してブロックを生成する | 認められたquantumを一度だけ消費する |


### 3.2 REAL / Attempt


REAL / Attemptは、基本となる新規計算提出系として維持する。


新規計算の受理、生成条件、実行commitment、bond予算、適用target、帰属を検証する。


Receiptや搬送メッセージだけで、無制限に新規計算が発生したことにしてはならない。


Attemptが乱数源として使われる場合、その資格は別途定義する。**「ブロックとして受理された」ことだけを、検証用beaconとしての適格性と同一視しない。**


### 3.3 EXEC / ROUND


EXEC / ROUNDの本質は搬送であり、独立ブロックであることではない。


次の形式を、version付きの搬送profileとして認め得る。


```text
通常ブロック内のtransaction / payload
複数メッセージのbatch
既存ブロックへの進捗・証拠の同梱
規定された専用carrier
```


独立したEXEC／ROUNDブロックを必須にしない場合も、順序、認証、課金、bytes上限、再送、期限、状態反映の意味は保存する。


この方針は、既存のexecution-laneのpermit、fee、weight規則を自動的に廃止するものではない。既存専用ブロックの撤廃には、対応する互換性設計と有効化が必要である。


### 3.4 Receipt / PFS4


Receipt経路では、計算した者と、後にブロックを組み立てる者を分離する。


添付原稿が参照する[PFS4実装](../../consensus/core/src/palw_receipt_v4.rs)では、executorがclaim・quantum範囲・beacon規則・builder fee・期限等を認可し、別のbonded builderがReceiptブロックを作る構造になっている。Miner側の報酬はexecutor bondの登録済みpayoutに帰属し、builder feeは別に扱う。今回、実装の動作や稼働有効化を確認したという意味ではない。


本書では次を必須とする。


**未成熟権利を使わない。** 権利確定、必要な認証、成熟、抽選、利用窓を経たquantumだけを消費する。


**二重消費しない。** 同じ候補チェーン上の同じ`claim_id + quantum_index`を二回消費しない。reorgでは、そのチェーン状態に対応して消費を巻き戻す。


**帰属を変えない。** BuilderやRelayが、executor、payout、許容fee、認可範囲を変更できないようにする。


**再推論を要求しない。** 成熟した権利の適格な消費に、新しいLLM推論を要求しない。ただし署名・ブロック構築・通常の検証は残る。


### 3.5 共通形式と時間差


三つの経路で、署名形式、claim参照、証拠参照、搬送形式を共通化してよい。


ただし、次の時間差は維持する。


```text
新規計算提出
    ↓
検査・異議・claimの状態遷移
    ↓
必要なSecurityCertified
    ↓
Receiptの成熟・抽選・利用可能期間
    ↓
quantum消費・ブロック生成
```


共通envelopeになったことを理由に、成熟待ちを削除してはならない。


### 3.6 FinalとSecurityCertified


`Final`、`SecurityCertified`、Receipt成熟、報酬の利用可能性は別に管理する。


Gate Cを適用するprofileでは、`Final`だけで合意creditを与えない。必要な抽選検証者の承認と公開告発期間等を満たした`SecurityCertified`を要求する。これは[RFC-0018](../rfc/0018-dag-parallel-multi-model-consensus.md)の区別に従う。


旧profileのclaimを、新profileの条件で暗黙に再解釈してはならない。


### 3.7 三つの区分とモデル別DAG生成


各モデルは、適用profileの条件を満たすREAL / Attemptをそれぞれ生成できる。Receipt / PFS4についても、各モデルに帰属する成熟権利を、認可されたBuilderが他モデルの処理と並列に消費してブロック化できる構造とする。


EXEC / ROUNDは、モデルごとの進捗・資料・対話を並列に搬送する。共通の搬送形式やBuilderの利用を、全モデルを一つのブロック生成列へ直列化する条件にしてはならない。


並列化は既存の親・challengeへの拘束、認証、成熟、一回限りの権利消費を解除しない。

## 4. Heartbeat・FallbackとLiveness


### 4.1 Livenessを分ける


| 対象 | 維持する進捗 | 自動的には保証しないこと |
|---|---|---|
| Chain liveness | 許可されたブロックと論理時計の進行 | LLM計算の認証 |
| Transport liveness | claim、資料、Court応答の搬送 | 搬送内容の正しさ |
| Verification liveness | 検査・異議・裁定の進行 | 全検証者不在時の認証成功 |
| Economic liveness | 条件を満たした権利・報酬の処理 | 未認証claimの支払い |


### 4.2 Heartbeat


Heartbeatは、通常の有用計算による生成が停滞した場合の、**限定された生存維持経路**とする。


モデル計算を行っていないHeartbeatに、モデル計算と同じ経済権利や計算認証を与えてはならない。添付原稿のbounded・fee-onlyという位置づけを維持し、具体的な受理・会計は適用profileで定める。この記述は、今回のruntime確認を意味しない。


Heartbeatによって、次を代替してはならない。


```text
不足しているPanel承認
実行されていない検査
認証待ちclaimのSecurityCertified
Receiptの認証条件
適格性を満たさないchallenge乱数源
```


### 4.3 Fallback


Fallbackは、既存の安全条件を外さずに進捗を回復するために使用する。


Relayの切り替え、資料配信先の切り替え、適用policyに従うPanel再選出、対応済み軽量profileへの新規jobの切り替え等は、既存のclaim identityと責任を壊さない範囲で行う。


未完了claimを別モデルへ置き換え、元の計算が完了したことにしてはならない。


### 4.4 期限


合意上の期限は、適用policyで定義されたチェーンの論理時計に基づく。ローカルPCの時計や、単一RPCのtimeoutだけをslash根拠にしない。


chain停止中に壁時計だけで正常参加者の期限を消費させることを避ける。再開後の期限処理は、全Nodeが同じ規則で再現できるようにする。


### 4.5 証拠と応答の搬送


Court関連の搬送には、通常jobの混雑と競合しても必要な応答を提出できる資源計画を設ける。


ただし、無制限の無料優先搬送にはしない。適格な要求、bond、fee、claim単位の総量上限を組み合わせ、DoSを抑制する。


### 4.6 停止・退出


MinerやPanelが停止する場合、新規義務の受付停止と既存義務の終了を分ける。


資料保存、応答、署名が必要な期間中にPCを停止できるのは、それらを適格なサービスへ委託し、必要な経路が維持される場合に限る。


**Heartbeatが動いていることを、すべてのclaimが完了できることや、bondを解放できることの証拠にしてはならない。**


### 4.7 モデル別の進捗と障害分離


モデルAの推論遅延、Panelの応答待ち、資料不足、Courtが、依存関係のないモデルB・Cの有効なブロック生成を一括で停止させる構造にしてはならない。


未処理claimをモデルごとに分離し、適格な他モデルのブロックは共通DAGへ取り込めるようにする。これは共通の合意規則や必要な認証を免除する意味ではない。


一モデルの停止だけを理由に全体をHeartbeatへ強制移行させず、稼働中の他モデルによる有用計算の生成を継続できることを目標とする。実際の切替条件・期限・資源配分は適用policyに従う。

## 5. 自分のNodeを持たないPermissionless参加とBond管理


### 5.1 Node-lessの意味


Node-lessとは、**利用者が自分のfull nodeを運用しなくてよい**ことを意味する。


ネットワーク上のNode、検証、状態管理、資料提供、Courtを不要にするものではない。


[Remote Client設計](../rfc/0009-palw-remote-miner.md)に従い、鍵・bond・署名を利用者側に残し、任意Relay、資料提供者、公開redemption builderに役割を分離する。


### 5.2 参加フロー


```text
Walletで鍵・payoutを管理
    ↓
公開規則に従ってbondを作成・有効化
    ↓
モデルと実行profile、chain情報を取得
    ↓
ローカル推論
    ↓
claimと必要なtransaction全体へ署名
    ↓
任意Relayへ提出
    ↓
inclusionとclaim状態を追跡
    ↓
Panelとの対話・必要資料の提供
    ↓
認証・成熟
    ↓
任意Builderによる許可範囲内のReceipt利用
```


専用pool、genesis operator、特定のホスト事業者からの許可を参加条件にしてはならない。bond、fee、対応profile、資源制限等の公開条件は残る。


### 5.3 非保管型の鍵・資金管理


Relay、Panel、Builderへ、利用者の秘密鍵やbond元本の支配権を渡さない。


署名はclaimのpayloadだけでなく、必要なfunding input、fee、change、payout等の改変を防ぐ範囲を覆わなければならない。


限定的な送信委任やredemption authorizationを、資金引出し・報酬先変更・任意transactionへの包括的な委任にしてはならない。


### 5.4 Bondの責任管理


Bondは、少なくとも次を分離して追跡する。


```text
総元本
新規義務へ利用できる余力
claim・Panel義務に予約済みの担保
既に消費した発行・報酬・weight予算
残存するslash責任
退出要求
最早再利用時点
最早引出し時点
```


同一元本を、複数モデル、複数claim、MinerとVerifierの役割に重複して無制限に計上してはならない。


**予算再利用可能時点と、担保引出し可能時点は同じとは限らない。** 未解決Courtや残存責任がある限り、必要な徴収可能担保を維持する。


### 5.5 Remote情報の信頼境界


Remote clientは、どの情報をどの方法で確認したか表示する。


単一RPCの回答、複数RPCの一致、検証可能なchain evidenceを区別する。複数RPCへの照会は運用上の防御になり得るが、それだけでtrustlessな検証とは呼ばない。


RelayのACKはchain inclusionではない。clientはtx ID、claim ID、inclusion、認証、成熟、消費を別々に追跡する。


### 5.6 自動応答


通常運用では、ローカルagentまたは限定委任されたresponderが、適格な要求にcacheから応答できるようにする。


Miner自身の追加計算が必要な場合だけ、その範囲と期限を通知する。


responderは、commitmentの変更、payoutの変更、bondの引出し、未承認モデルの実行を行ってはならない。

## 6. モデルの売買対象となるModelPosition


### 6.1 何を売買するか


ModelPositionは、固定されたモデル登録に紐付く、プロトコル上のポジションとする。


モデルの重みそのもの、著作権、登録者の秘密鍵、claim所有権、bond、将来のマイナー報酬を自動的に移転するものではない。


[既存設計](../adr/0087-a-position-is-bought-from-the-curve-and-sold-back-to-it.md)では、ModelPositionは自由譲渡型のERC-20ではなく、**モデル別の曲線から購入し、その曲線へ売却する非譲渡型ポジション**である。この構造を維持する。


### 6.2 固定された市場対象


市場の参照先は、不変のmodel registration IDとする。


モデル更新時に、既存Position、保有残高、reserve、価格、retired unitsを新モデルへ自動移行しない。


新モデルの登録が、他モデルの市場状態を変更してはならない。


### 6.3 会計と状態の正本


ModelPositionの残高、市場reserve、供給、売買、retirementは、共通の決定論的状態遷移で管理する。


Native経路とEVM経路が存在する場合も、同じ状態を参照・変更する。別々の独立台帳を作り、二重発行や残高不一致を許してはならない。


### 6.4 売買条件


購入・売却には、対象モデル、数量、許容価格または最小受取量、期限、所有者認証、適用feeを拘束する。


価格計算、整数丸め、overflow、供給変化、fee配分を決定論的に定義する。


virtual reserveを使用するprofileでは、virtual reserveを実際に払い出せる資産として扱わない。売却による支払いは、実reserveと保護される下限の範囲内に制限する。


### 6.5 計算経済との接続


モデル利用に伴うbuybackやretirementを設ける場合、その財源・割合・対象・実行時点を明示する。


同じ報酬をMinerに全額支払った後、存在しない別予算からbuybackを実行したことにしてはならない。


登録者への売買手数料と、Miner・Verifierとして働いた対価を分離する。ModelPositionの保有だけで、計算認証権、Panel席、consensus weight、bond資格を与えてはならない。


### 6.6 表示上の境界


ModelPositionについて、配当、元本保証、価格上昇保証、モデルの所有権を表示してはならない。


付随するアクセス特典等がある場合は、その提供者、内容、期限、提供責任を別に示す。オンチェーンの保有証明と、オフチェーン特典の実際の提供は同一ではない。


本節は技術上の権利範囲を定義するもので、法的分類を断定するものではない。

## 7. Miner・Panelの不正と、正しい計算を扱う仕組み


### 7.1 安全性の前提


安全性の説明では、少なくとも次を明示する。


```text
正直な検証者の割合と抽選方式
対象モデル・資料を取得できる範囲
検査が対象とする演算・関係
challengeの独立性と操作可能性
Courtの資源上限と応答期限
徴収可能な担保
公開告発と搬送の利用可能性
```


測定・導出できていない値は`UNKNOWN`と表示する。


### 7.2 主な不正と処理


| 不正・障害 | 処理の原則 |
|---|---|
| Minerが誤った演算結果をcommit | 認証済み資料から局所化し、exact Courtで裁定 |
| Minerが必要資料を出さない | 適格な要求と期限に基づく開示義務違反として処理 |
| Panelが検査結果を捏造 | 署名済み主張と客観的資料の不一致を追及 |
| Panelが両立しない承認を署名 | Equivocation evidenceで処理 |
| Panelが正しいMinerを虚偽告発 | Nodeが証拠を検証し、成立しない告発を棄却 |
| MinerとPanelが共謀 | 公開verifierによる追及、認証条件、担保上限を維持 |
| Relayが提出を握り潰す | 別Relayへの冪等再送とchain inclusionの確認 |
| 同じ権利を重複提出 | 候補チェーン状態の一意性・消費規則で拒否 |


### 7.3 Panelも最終裁定者ではない


Panelの多数決、単独承認、operatorの判断だけで、計算不正を有罪と判定してはならない。


不正裁定は、認証された証拠と決定論的な判定規則に基づく。


正常なMinerやPanelを、他者の任意の主張だけでslashできないことを必須条件とする。


### 7.4 正直なサンプリングの見逃しと不正を区別する


サンプリングで不正を見逃したことと、Panelが虚偽の検査を主張したことは同じではない。


Panelの承認後にclaimが反証された場合の責任は、適用policyに従う。厳格な保証責任を負わせる場合は、その責任範囲、担保、期間、徴収条件を参加前に明示する。


**「全体に誤りがあった」という事実だけから、「Panelが検査を実行しなかった」と推定してはならない。**


### 7.5 正しさの表現


通常経路で表示できるのは、対象検査への適合、必要な承認、異議期間等を満たした**条件付きの認証**である。


Courtで局所演算の一致を確認しても、それだけで全計算を認証しない。また、計算結果と証拠の整合性から、特定の物理CPUが過去に全演算を実行した事実まで証明したと主張しない。


### 7.6 閉鎖モデルと共謀の残余リスク


正しいモデルを誰も取得できない場合、実効的な不正検出能力が失われ得る。


既存前提は、その場合の検出確率を根拠なく仮定せず、bond当たりのBlock・Reward・Final Weight等の上限で経済的被害を有界化する。一方、未認証claimに合意creditを与えない区別は維持する。


正直な検証者に関する前提が破れた場合まで、無条件に安全と説明してはならない。


### 7.7 Privacy


チェーンにprompt本文を保存しないことと、Panelや資料提供者に本文が見えないことは異なる。


claim参加前に、検査・Courtで必要になる開示範囲を示す。秘密情報を含む仕事は、開示条件に同意できる場合だけ提出する。


commitmentや暗号化保存だけを理由に、検証時の秘匿性を保証してはならない。

## 8. モデル＝minerを前提とするDAG並列ブロック生成


### 8.1 固定する前提と目的


**MISAKAは、モデル＝minerとして、各登録モデルをDAG上の独立した論理的な採掘主体として扱う。各モデルを実行するminer群が、それぞれの計算・検証・生成条件に従い、並列にブロックを生成して共通DAGへ接続できる仕組みを前提とする（MUST）。**


この前提は、2026-11-03のユーザー指定である。DAGで複数のminerが並列にブロックを生成・接続する構造を、モデル単位の生成にも活かすことを目的とする。


本仕様が求めるのは、単なる「複数モデルによる並列推論」ではない。モデルA・B・Cの結果を一つの生成者へ集め、その生成者だけが順番にブロックを作る構造を、必須の合意経路にしてはならない（MUST NOT）。


モデルAが長い推論を実行中でも、モデルBやモデルCがそれぞれの条件を満たしたブロックを生成できることを要求する。全モデル共通の実行完了待ち、一括Panel承認待ち、唯一の全体proposerによる順番待ちを導入してはならない。


これは自身のclaimに必要な検証・生成条件を省略する意味ではない。また、モデルごとに別のチェーンや独立した最終合意を作る意味でもない。**生成はモデルごとに並列、受理・merge・会計・合意規則は共通DAGで統合する。**


### 8.2 「モデル＝miner」の意味と責任の分離


| 概念 | 本書での意味 |
|---|---|
| Model Miner（論理的な採掘主体） | 固定Model IDに対応する計算・検証・ブロック生成の経路。新しいwire型や特権主体の追加を意味しない |
| Miner / Executor（実参加者） | そのモデルを実行し、claimと生成物へ署名し、bond責任を負う参加者 |
| Panel / Verifier | 対象claimを検査し、承認または不正追及を行う参加者 |
| Builder / Relay | 規定された認可に基づき、ブロックの組立てや提出を行う参加者 |
| Node | 共通DAGと決定論的状態を管理する検証主体 |


一つのモデルを複数の独立Minerが使用してよい。一人のMinerが複数モデルを実行してもよい。ただし各claimのModel ID、署名者、bond予約、報酬帰属を曖昧にしてはならない。


「モデル＝miner」を理由に、モデル登録者だけに採掘権を与えたり、一モデルにつき一つの物理Node・鍵・bondに限定したりしてはならない。ModelPositionの保有を、生成主体としての必須資格に追加してはならない。


並列性の単位と責任の単位は分ける。モデル単位で生成経路を並列化しても、個々の実行者と承認者の責任は、署名とbondへ拘束する。


### 8.3 共通DAGへの並列生成と接続


概念上の生成経路は次のとおりとする。


```text
モデルAを実行するMiner群 → Aの計算・検査・生成条件 → A由来のブロック ┐
モデルBを実行するMiner群 → Bの計算・検査・生成条件 → B由来のブロック ├→ 共通DAG
モデルCを実行するMiner群 → Cの計算・検査・生成条件 → C由来のブロック ┘
```


既知の親Pから同時に生成される例は次のとおりである。矢印は説明上の「親から子への接続」を表し、wire上の参照方向を新たに定義するものではない。


```text
P → A1    モデルAによる生成
P → B1    モデルBによる生成  } 同じ親からでも並列に生成できる
P → C1    モデルCによる生成


{A1, B1} → A2    後続ブロックが複数の適格な親を参照する例
{B1, C1} → C2    別モデルも並行して生成を続ける例
{A2, C2} → B2    生成した枝を共通DAGで接続・mergeする例
```


この例は全モデルが必ず同時に生成すること、各段階で全tipを参照すること、専用のmerge担当者を置くことを要求しない。現実のモデルごとの実行速度・生成条件の違いを許容する。


同じ親から作られたことや、別モデルの同時ブロックが存在することだけを理由に、一つを残して残りを単一チェーンの競合ブロックとして一律に排除してはならない。規定のDAG受理・資源条件の範囲で、並列候補として保持・検証・接続する。


モデル内だけで親を固定し、モデルごとに孤立したチェーンを作る設計にしてはならない。親選択では、適用規則に従い、取得済みの適格な他モデル由来のtipも参照できるようにする。未取得・不適格な親の参照や、親数・mergeset上限の解除は要求しない。


### 8.4 モデルごとの独立した生成経路


各モデルの生成経路は、概念上、次の責務を持つ。


```text
固定モデル・実行profileの選択
  → 自身のbond・生成予算・実行条件の確認
  → 経路に応じた親・challenge・実行への拘束
  → 有用計算と必要な資料のcommit
  → 対象claimの検査・認証・必要な状態遷移
  → 当該ブロック種別の生成条件判定
  → 署名・任意Relay/Builder経由の提出
  → 共通DAGでの検証・接続・決定論的処理
```


この図は責務の概念整理であり、Attempt、free-prompt、Receiptの異なる時間順序を単一のwire手順へ置き換えるものではない。第3章の経路ごとの条件を優先する。


REAL / Attemptでは、そのモデルの新規計算を用いて生成する。Receipt / PFS4では、そのモデルに帰属する認証・成熟済み権利を認可範囲内で消費する。EXEC / ROUNDは各モデルの進捗と対話を搬送し、必ず独立ブロックにすることは要求しない。


生成可能になったモデルは、無関係な他モデルの実行完了を待たない。長時間の推論中に親やchain状態が変化した場合は、適用profileの有効性判定に従う。並列生成を理由に、古い推論を新しい親・challengeへ無署名で付け替えてはならない。


### 8.5 四つの並列性を同時に維持する


| 並列性 | 対象 | 必須の境界 |
|---|---|---|
| 実行並列性 | 複数モデル・複数jobの同時推論 | モデル同一性と各実行のcommitmentを維持する |
| 検証並列性 | 複数claimを異なるPanel・Verifierが並行検査 | 各claimの認証条件・Court・責任を維持する |
| 生成並列性 | 各モデルの実行者・認可されたBuilderによる同時ブロック生成 | 全モデル共通の単一proposerを必須にしない |
| DAG並列性 | 同時生成された複数ブロックの保持・接続・merge | 共通の受理規則・一意性・会計に収束させる |


実行と検証だけを並列化し、生成を全体で一本化した実装は、この前提を満たしたとは扱わない。


複数モデル対応を、すべてのNodeがすべてのモデルを実行する構造にしてはならない。Nodeは必要な認証と有界な証拠を検証し、各モデルの全量推論を通常要件としない。


### 8.6 モデルごとの独立性と障害分離


各claimは、自身のModel ID、実行profile、executor、資料、検証policy、bond予算に拘束する。


モデルAの正常な検査結果を、モデルBの認証に流用してはならない。


一つのモデルの資料欠落やCourtが、無関係なモデルの推論・搬送・検査・ブロック生成を無制限に停止させないよう、queue、memory、通信、検査予算を分離する。


Panelの共有は可能だが、共有Panelの運用都合を理由に、全モデル一括承認のbarrierを必須にしてはならない。個別に認証されていないclaimを進めず、進められる別claimは進める。


ただし、明示的なjob依存関係、同一bondの共有予算、共通DAGの合意上必要な依存は残る。「独立」はそれらを無視する意味ではない。


### 8.7 DAGでの受理と計算creditの分離


異なるモデルが同時に生成したsibling blockやclaimを、単一proposerの選択だけで排除する構造にしない。[RFC-0018](../rfc/0018-dag-parallel-multi-model-consensus.md)が扱う多モデルの並行生成と、共有上限で競合した場合の順序依存の解消に接続する。


ただし、同時生成されたすべての提出物が無条件に報酬を得るわけではない。ブロックのDAG上の受理、claimの受理、検査、SecurityCertified、報酬、合意creditを区別する。


BLUE/RED等のDAG上の分類だけを、個々のclaimの算術的正しさや報酬資格の代わりにしてはならない。適用する合意規則に従って、各claimを独立に記録・検証・帰属させる。


共有予算・重複・bond余力・資源上限による採否は、再現可能な規則で決定する。DAGに複数のブロックが存在することを理由に、未認証claimへcreditを与えたり、同じ仕事を複数回支払ったりしてはならない。


### 8.8 決定論的なmergeと競合処理


同じ適用policy、同じ受理済みDAG、同じ開始状態を処理するNodeは、受信順、ローカルthread数、RPCへの到着順にかかわらず、同じ採否・予約・報酬・weightを得なければならない。


独立したbranchに存在する提出物の仮状態と、merge後の共有予算消費を区別する。merge時には重複消費を拒否し、reorgでは予約と消費を対応する状態へ戻す。


特に、異なるモデル・異なるbranchで同じbond元本を使った予約、同じclaimやworkの再提出、同じReceipt quantumの競合消費を、共通状態上で一意に処理する。


競合する集合を処理するための決定論的な順序付けは、ブロック生成前に一人のproposerへ許可を集約する仕組みとは異なる。**生成段階では並列性を維持し、統合段階では採択された規則によって一貫した結果を得る。**


### 8.9 複数モデルによる一つの仕事


モデルAの出力をモデルBの入力にする場合は、仕事の依存関係を明示する。


```text
Claim A
  output commitment
       │
       ▼
Claim B
  input commitmentがAの対象出力を参照
```


このようなjobの依存関係と、共通DAG上のブロックの親子関係を混同しない。あるモデルのブロックを親として参照するだけで、そのモデルの推論出力を自分の入力に使ったことにはならない。


下流の成功を、上流claimの検証の代わりにしてはならない。


複数claimをまとめた集約結果を提出する場合も、子claimとの対応を保持する。単に結果を結合しただけで、子claimと同じ計算量を再び新規workとして計上しない。


### 8.10 計算量・生成機会・公平性


仕事を細かく分割しただけで、総報酬・ticket・weightが増える設計にしてはならない。


モデル別の生成機会は第9章の配分、個別bond予算、認証条件に従う。モデル数や論理的な生成経路を増やしても、ネットワーク全体の発行予算と同一資本当たりの上限は増えない。


同じ速度、同じブロック数、全モデルの同時当選、各モデルへの無条件の最低枠は、本書の並列性要件には含めない。適格な複数モデルの生成を、設計上の不要な直列待ちで塞がないことが要件である。


モデルサイズ、context長、分割方法による検査費用の差を測定する。「同じ計算量なら同じ純利益になる」といった経済的公平性は、測定なしに保証しない。


### 8.11 実装・適合性・有効化の境界


今回の追加は、モデル別にブロックを並列生成するという構造上の前提を固定する。具体的なparent選択、DAG幅、BPS、k、mergeset上限、生成枠、認証席数、deadline、wire形式、activation高さの新しい値は割り当てない。


実装は、並列推論のデモだけでなく、異なるモデルから実際にブロックを生成し、Nodeが共通DAGへ取り込み、merge後に報酬・予約・weight・一意性を一致させる経路で確認する必要がある。


少なくとも、同一親からの同時生成、異なる親からの生成と後続merge、モデルごとの速度差、一モデルの停止、Panel遅延、共有bondの競合、Receipt二重消費、reorgと再起動を試験する。


既存の実装がこの条件を満たすと今回宣言するものではない。採択済み詳細方式との不一致は記録し、設計凍結規則に従って解消する。

## 9. Miner・Verifier・Builderへの経済的インセンティブ


### 9.1 対価の分離


| 役割 | 対価の対象 | 対価を発生させないもの |
|---|---|---|
| Miner | 規定に適合した計算と、利用された計算権 | 未認証の自己申告、重複work |
| Panel / Verifier | 規定された検査・応答・証拠構築 | 無条件の承認署名、検査実態のない提出 |
| Public Challenger | 成立した告発・適格な証拠への報酬 | 根拠のない告発、同じ証拠による重複請求 |
| Builder / Relay | 認可された搬送・ブロック構築 | executor報酬の横取り |
| モデル登録者 | 規定された市場手数料、自身が担った実行・検証の対価 | 登録したという理由だけでのMiner報酬の直接取得 |


### 9.2 Panelに負担を移すための財源


Panelに証拠構築を担当させる以上、その費用の負担元を明示する。


```text
Panelの必要収入
  ≥ 検査計算費用
    + 証拠構築費用
    + 保存・通信費用
    + 提出手数料
    + 担保拘束に伴う費用
```


これは各参加者の利益を保証する式ではなく、継続参加可能性の評価条件である。


不正発見時の賞金だけに依存すると、不正が少ない正常運用で検証者が維持できない。そのため、通常の検査対価と不正告発報酬を分離する。参照する[経済分析](../design/palw/economics/econ-verifier-incentive-and-allocation.md)でも、bounty-onlyの検証者報酬と、正常claimの検査費用回収は別問題として扱われている。


### 9.3 支払予算


検査対価、Miner報酬、Builder fee、市場への配分は、それぞれ財源と受取条件を定義する。


同じ予算を複数の役割へ重複して全額配分してはならない。


```text
各報酬の支払総額
  ≤ 適用規則で承認された発行予算
    + 徴収済み手数料
    + 対象用途に利用できる支払済みescrow
```


Slashによる担保移転は別会計とする。没収担保、告発者配分、burn、既払い報酬を混同しない。


Panelが作成したメッセージ数だけで無制限に報酬が増える設計にせず、claim・検査範囲・責任に対応する予算上限を設ける。


### 9.4 Bond当たりの上限


同じbond資本・同じ期間について、次を別々に制限する。


| 上限 | 対象 |
|---|---|
| Q | claim発行・処理能力 |
| B | 経済的なブロック生成能力 |
| R | 報酬総額 |
| F | Final後に認める合意weight |


計算を省略したり、claimを高速生成したりしても、この上限を超えられないようにする。


同時予約だけでなく、期間中の消費履歴、再利用、退出直前の集中提出、複数役割への重複計上も制限する。


### 9.5 モデル別配分


モデル別配分は、適格なMiner・Verifier資本の重複のない集計を基礎とする。


添付原稿と[パラメーター台帳](../governance/parameter-register.md)を参照する基礎式は次とする。


```text
A_m = c_m · (S̄_m)^1.5
```


ここで、`c_m`はモデル階層係数、`S̄_m`は適格bond資本の7日相当の平均とする。係数は配分重みに一度だけ適用し、受理後の報酬へ重ねて掛けない。旧資料の30日表記を現在の基準値として流用しない。この値を今回変更したり、稼働ネットワークでの適用を宣言したりするものではない。


登録モデル全体の上限、上限適用後の正規化、減額分の扱いは、採用されたpolicy版に従う。台帳と旧ADRに異なる記述が残る場合、実装で都合のよい方を暗黙に選択してはならない。


合意実装の計算は、規定された整数演算・丸めで再現可能にする。


### 9.6 モデル公開の経済的誘因


モデルを共有することで外部のMiner・Verifierが参加し、実際の適格bondと検証可能性が増える構造を目指す。


ただし、モデル全体への配分増加と、登録者個人の利益増加は分けて評価する。


登録者が自己資本を追加する場合との比較、資本集中、大規模運用者の優位、複数名義での参加を評価する。チェーンが「公開モデル」というラベルだけで価値や安全性を認定する構造にしない。


### 9.7 Slashと自己告発


不正への処罰は、徴収可能な担保と適用責任に基づく。


攻撃者が自身の別名義から告発して報酬を回収する場合も含め、**実際の純損失**を評価する。名目上のslash額だけで抑止力を説明しない。


告発者報酬、資料要求者への配分、返還、既払い報酬を合算しても、自己不正と自己告発が利益を生まないことを検証する。


### 9.8 期待利益と残余リスク


評価では、概念上、次を区別する。


```text
不正の期待利益
  = 不正成功時の利益
  + 回収できる告発・関連報酬
  - 検出・徴収される期待損失
  - 攻撃費用
```


実効的な検出確率、外部利益、徴収可能額が不明なら、その値を`UNKNOWN`として残す。


「常に不正が不利益になる」と保証してはならない。既存前提に従い、検出能力の評価と、bondによる被害上限、認証されていないclaimの合意credit禁止を別々に維持する。


### 9.9 モデル別配分とDAG並列生成の接続


モデル別配分は、各モデルの生成機会と経済的な上限へ適用する。配分計算を、全体で一モデルだけを唯一のproposerとして動かすための直列化条件にしてはならない。


複数モデルが同時に生成条件を満たす場合、それぞれが並列にブロックを生成できる構造を維持し、共有上限の競合は共通DAGの決定論的な処理で扱う。


「モデル＝miner」は、モデル数に応じて発行予算を複製する規則ではない。モデルの多数登録、同じ仕事の別モデルへの付け替え、同一bondの重複割当によって総報酬・creditを増やしてはならない。


報酬は各実行者・検証者・Builderの規定された役割へ帰属させる。モデルを論理的な生成主体と呼ぶことを理由に、モデル登録者やPosition保有者へMiner報酬を自動的に付け替えない。

## 適合性確認


本仕様に適合した実装と表示する前に、以下を対象profileの実際のNode経路で確認する。


| 章 | 必須の確認 |
|---|---|
| 0 | 通常時にMinerへ証明専用の全量再推論を要求せず、実用出力と提出対象が対応する |
| 1 | 同一Model IDの実行意味を変更できず、新登録が既存市場・責任を変更しない |
| 2 | 正常claim、算術不正、資料不開示、誤告発を別々に正しく処理する |
| 3 | 未成熟Receiptと二重消費を拒否し、EXEC搬送だけでは新規計算権が増えない。各モデルの生成経路を不要に直列化しない |
| 4 | Heartbeatやfallbackが認証条件を迂回せず、停止・再開時の期限処理が一致する。一モデルの停止で無関係なモデルの生成を止めない |
| 5 | 悪意あるRelayでも鍵・bond・payoutを奪えず、再送・再起動・reorg後も追跡できる |
| 6 | Positionの二重発行、無許可移転、virtual reserveの払出しを拒否する |
| 7 | 不正なPanelが正常Minerを任意にslashできず、public challengerが客観的裁定へ到達できる |
| 8 | 複数モデルが実際に並列でブロックを生成・接続でき、異なる到着順、DAG merge、共有予算競合でNode間の結果が一致する |
| 9 | 発行・手数料・担保・市場の会計が保存され、自己告発、分割提出、モデル数の増加で予算が増えない |


### 第8章の必須試験シナリオ


以下は試験要件であり、今回の実測結果ではない。


| ID | シナリオ | 確認すべき結果 |
|---|---|---|
| DAG-01 | 異なるモデルA・Bが同じ既知の親から同時に有効ブロックを生成 | 単一proposerの許可を必須にせず双方をDAG候補として扱う。最終的なcreditは各claimの条件で判定する |
| DAG-02 | A・Bが異なる親から生成し、後続ブロックが双方の枝を参照 | 適用する親数・mergeset上限内で共通DAGへ接続し、モデル別にチェーンを分断しない |
| DAG-03 | Aは長時間推論、Bは短時間推論、Cは停止 | 適格なBの生成をAの完了やCの復帰待ちにしない |
| DAG-04 | AのPanel・Courtが遅延、Bの個別条件は成立 | Aの未認証creditを進めず、無関係なBの生成・処理は継続できる |
| DAG-05 | 複数モデルが同一bond余力を競合消費 | merge後に予約・支払・weightが上限を超えず、Node間で同じ結果になる |
| DAG-06 | 複数Builderが別branchで同じReceipt quantumを消費 | 共通状態で一回だけ有効に消費し、reorg後も対応する状態へ戻る |
| DAG-07 | 同じ対象DAGを異なる順序で受信し、再起動・再構築 | 同じ適用policyと開始状態から同じ採否・帰属・会計へ収束する |
| DAG-08 | 同一モデルの複数Minerと、一Minerによる複数モデル実行 | Model IDと実際の署名者・bond・payoutを分離して追跡し、独占権や重複予算を発生させない |
| DAG-09 | 同じ仕事の分割・再送・別モデルへの付け替え | 実行同一性と予算の規則に従い、二重報酬・二重creditを拒否する |


測定対象には、Minerの追加CPU時間・memory・保存量、Panelの検査費用、Courtの最大bytes・round数・局所計算量、期限内搬送能力を含める。


モデル別のブロック生成待ち時間、推論・検査・親選択・搬送・mergeの各待ち時間、DAG幅、資源使用量、同時生成時の採否も分けて記録する。実測なしに並列化によるthroughput向上や公平性を保証しない。


**本書の作成時点では、これらの試験を実施していない。文書の存在、コードの存在、単体試験の存在、稼働ネットワークでの有効化を、それぞれ別の状態として記録する。**

## 維持する中核構造


> **Minerは、自分が必要とするLLM推論を行い、その結果を実用に使う。Panelは、その実行に拘束された資料から検査と証拠構築を担う。Minerの追加計算は、適格な対話で必要になった限定範囲に留める。Nodeはモデル全体を実行せず、公開された規則と有界な証拠によって状態を更新する。**
>
> **新規計算の提出、資料・進捗の搬送、成熟した計算権の消費は分離する。形式を共通化しても、認証・成熟・責任・一回限りの消費という境界は消さない。**
>
> **モデル＝minerを前提に、各モデルがそれぞれの生成条件を満たすブロックを並列に生成し、共通DAGへ接続する。単一の全体proposerに集約せず、生成の並列性と、merge後の決定論的な合意・会計を両立させる。**
>
> **モデル登録、claim認証、bond管理、ModelPosition、市場価格、報酬を混同しない。どの主体も、署名や運用上の地位だけで計算の真実を決定できない。**
