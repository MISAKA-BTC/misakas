## Missing boundary and mechanism

Accepted Typed replacement and current-positive cold reads do not establish behavior when its actual selected-parent authority is rolled back while provider files and virtual UTXO acceptance remain present. The new test exercises that real consumer boundary. It introduces no production behavior change and does not assume a production defect without an observed failure.

The separate public filter is `rfc08_typed_replacement_native_reorg_restart_keeps_material_and_reaccepts_identical_carrier`. It opts into the existing proven role driver with `MISAKA_TYPED_REORG_CHILD_V4=1`, after its actual initial job/seal, complete signed SDK TypedKernelV4 material, native funded admission, claim admission, bounded signed replacement and all four cold current-positive provider reads. The original two filters keep their previous scopes.

The writer retains the exact signed and funded replacement transaction and its canonical bytes. A separate real native node replays the actual prefix ending before that replacement, then mines a heavier branch. The first node must select that branch, agree with the independent replay's full state root, roll the monetary sequence from 1 to 0 and the recovery generation inventory from 2 to 1, and preserve the previously admitted original claim. No rows or journals are manually rewritten.

While replacement authority is withdrawn, the writer closes its real DB and the acquisition-only process cold-opens it and all four provider stores. The initial generation must have current native authority and answer; the withdrawn generation must receive checked `Denied` (not resource/unavailable) and refuse exact reads despite its retained physical material. All four snapshots remain held. An actual native finalized-release witness for a deliberately non-release accepted checkpoint must refuse GC and leave both material and restart-metadata bytes unchanged. No missing row/current-consent change is treated as deletion authority.

After this rollback-time native restart, the writer probes the actual saved input/change UTXOs, current virtual accepted transaction IDs and persisted selected-chain acceptance data. Only a genuinely restored input permits submitting the identical saved transaction again. If its input is already spent while its change and exact virtual acceptance remain present, and selected-chain acceptance is absent, one actual empty heartbeat must accept the original mixed-blue transaction. Every other observation fails. The actual run observed `input_live=false`, `change_live=true`, `virtual_accepted=true`, `chain_accepted=false`; the empty-heartbeat path completed and its actual acceptance data contained the saved transaction ID. The test never rebuilds the carrier, changes funding, re-signs the proposal or substitutes an authority. It requires restoration of sequence 1 and the exact original replacement consent, then repeats the cold native/provider role handoff and requires all four old-historical/new-current exact reads and stable restarted state root.

## Limits

The native writer remains explicitly unarmed for native resource admission. Acquisition-only readers open/warm the existing node before arming their declared metadata budgets, submit no native object/block, retain native state owners, and release every DB strong owner before the next process opens it. This is role composition, not whole-node physical quota or allocator coverage. The shared heartbeat harness still uses its legacy MutableBlock export. Tiny artifact/OPV eligibility seams, explicit unapproved private fences, skip-PoW and simulated clock remain visible.

The GC assertion is negative retention control only: no positive terminal release or prune authorization is fabricated. Typed positive release/GC, pruned IBD, controlled old-delta deletion, OS crash, K3, selected-verifier certification, reward settlement and campaign acceptance remain outside this test. No UNKNOWN campaign gate is promoted.
