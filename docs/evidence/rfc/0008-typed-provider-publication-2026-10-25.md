## Consumer gap and bounded change

`DurableMonetaryMaterialProviderV1::prepare_prospective_kernel_v4` receives independent borrowed native material, financial enrollment, restart context and recovery capsule. Previously it checked the financial enrollment against verified material, while the context archive checked its capsule against the context's manifest. It did not bind these two pairs together. A mismatched request/context or a capsule carrying different monetary fees could therefore publish retained bytes under the supplied enrollment consent and publish restart metadata under another identity. Later current-native restore correctly refuses such mismatched metadata, but the provider has already reported successful preparation.

The shipping endpoint currently passes fields from its own coherent native ingress grant. This change closes the public storage consumer's missing input invariant; it is not evidence that the endpoint currently constructs mismatched fields. Before candidate construction or either atomic disk publication, the consumer now requires the exact verified request ID, exact manifest, an initial `FundedEnroll` capsule, and equality of the monetary terms and ordered `(provider, collateral, prepaid fee)` tuples. These comparisons borrow their inputs and do not add hashing, serialization, deep copies or admission demand. Consent hashing is performed once and reused. Signatures remain outside the financial consent preimage and are still authenticated by native ingress; this guard does not confer signature authority.

## Native fixture

The new isolated role fixture uses the existing tiny `wide128_v1(7)`/K2-TIR-v2 mechanism artifact and explicit private policies. It posts an actual job and salted seal, obtains the own-node opaque producer candidate, and calls the SDK complete TypedKernelV4 handoff builder with the actual trace, inputs and every immutable parameter. The node's real `palw_kernel_material_ingress_v4` derives the funded enrollment and restart context. No accepted financial row, provider queue or claim is prefilled.

Independent wrong request, wrong context manifest with the correct request ID, non-funded capsule kind and wrong unsigned monetary fee must all refuse before either provider file changes. The positive path durably prepares real typed bytes, refuses an answer before native funding acceptance, signs and carries `FundedEnroll` through the real mempool/block/native fold, checks both native consent and exact admission APIs, then carries the salted claim under the active material gate. Finally it reopens the same native database and provider files and requests an exact current-native answer from the restored bytes. Both providers complete actual durable preparation before any provider signature is generated. Acquisition-only reader processes supply explicit 4 GiB RAM/4 GiB database logical ceilings because native ingress requires local metadata admission; these are local test ceilings, not measured policy costs or whole-node physical quota coverage.

The fixture retains the shared G14 harness's skip-PoW, simulated clock and test artifact/OPV eligibility seams. Its heartbeat path still uses the legacy MutableBlock export and does not establish render-allocation lifetime coverage. It is not a real K3 workload, production provider socket session, multi-process campaign, pruned IBD, OS-crash or replacement/reorg/prune acceptance test. The separate legacy GC fixture continues to have its original scope. No UNKNOWN campaign gate is promoted. The claim assertion establishes native ledger admission only; it does not establish selected-verifier certification, fork-choice credit or reward settlement.
