## Consumer defect and change

The node's `ConsensusGcOracleV3::release_finalized` accepted a finalized terminal receipt when its tail matched, while discarding the saved intent's `release_block`. `RemoteProofGcOracleV2` did the same. A positive current finalized receipt could therefore revalidate a deletion marker naming another release block.

Both actual adapters now use `receipt_matches_gc_intent_v4` in the shared remote `monetary_material_gc/native_v4.rs` leaf. Receipt root, covered historical consent, tail and saved release block must all agree. The block field remains an informational audit commitment in the consensus receipt schema; this is a local saved-GC-intent binding, not a new consensus authority rule. Native finality, exact generation history and current state authentication remain the native API's responsibility. A terminal receipt mismatch returns false without legacy fallback. A failed or capacity-refused native receipt read remains an error. Only genuine receipt absence retains the legacy delta/finality fallback.

## Actual-path fixture

`g14_kernel_route_e2e/material_gc_v4.rs` builds an actual signed small-program claim and verifies its complete legacy `KernelPositions` bundle against the native ledger. A provider publishes those bytes to its durable store before service signatures. A fresh covenant root explicitly lists that real claim as a signed dependency; it is not substituted for the claim itself.

The actual claim is accepted before the explicit private material fence at DAA 30, and its recorded commit DAA is asserted to precede that fence. The node then crosses DAA 30 and asserts both monetary and recovery policies active before any enrollment or replacement. This tests the explicit legacy historical dependency path; new claims under active recovery still require prospective funded `TypedKernelV4` material.

The test submits signed funded enrollment and bounded provider replacement through the existing mempool/template/native fold. It checks that saved signatures/material alone do not grant new-generation acceptance, then checks actual accepted generation history. A longer native branch from before the replacement withdraws that generation at the selected-parent native point. The test then distinguishes an actually unspent carrier input from a carrier already accepted in the virtual mixed-blue mergeset. The observed latter path commits the original carrier in the next actual block without resending or rebuilding it, and its native generation survives a real same-database restart. The old provider's material stays in its fsynced store through these changes.

The fixture waits for actual monetary/payment obligations to produce their tail, submits a signed Release under native finality/ancestry admission, then obtains the positive receipt from the native finalized-state API. Both native and authenticated paged op242 remote consumers must accept the correct historical/current consent tuple and refuse a different release block or tail. A refused physical GC retains the actual durable bytes. Controlled deletion of the old Release delta checks that positive current finalized receipt presence can still authorize the exact intended GC without that old delta. Reopening the provider verifies the accepted deletion is durable.

The fixture explicitly lowers local finality depth to 20 for bounded mechanism execution. This is not a network policy recommendation. It uses the existing small-program artifact/OPV eligibility seams, simulated clock, harness keys and skipped PoW. Controlled delta removal is not pruned IBD, and this legacy bundle test does not establish prospective `TypedKernelV4` provider replacement acceptance or K3. The shared `T12Chain` heartbeat test harness still extracts `MutableBlock` rather than transferring `BlockTemplate::into_immutable_v3`; therefore the GC case establishes no render-allocation ownership coverage. A broad heartbeat-harness migration is separate future work if this harness is used for a memory campaign. The actual DB ownership child below directly uses the new immutable owner, and the six production native submit exports were audited separately. The 15-gate campaign remains UNKNOWN.

## Final actual result

The final probe recorded `input_live=false`, `change_live=true`, `virtual_accepted=true`, and `chain_accepted=false` while the selected-parent recovery contract had returned to one generation and the actual provider bytes remained held. No carrier was rebuilt, rebound to another funding input, or double-spent. The test retains a separate exact-carrier reuse branch for the genuinely restored-input case; that branch was not the path observed in this run.

The accepted generation survived a same-database node restart. A signed native Release was carried across DAA 345→346 after the actual payment/retention tail became releasable under the fixture's native finality depth. Both the native finalized-receipt adapter and the all-pages-authenticated op242 remote adapter accepted the correct tuple for initial and final consents and refused a different release block or tail. After controlled removal of the old Release delta, the exact positive finalized receipt still authorized deletion; reopening the provider found its material durably absent. This is legacy `KernelPositions` mechanism acceptance, not prospective `TypedKernelV4` provider acceptance, K3, pruned IBD, OS-crash or multi-host evidence. It does not upgrade any UNKNOWN campaign gate.
