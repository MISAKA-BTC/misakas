## Task A — RFC-0023 (ADR-0186)

### Stage 1: already in the tree — connected, not duplicated
Found existing and wired: `consensus/core/src/palw_unresolved_bound_v1.rs` (fence `palw_unresolved_bound_v1`,
`palw_resolved_through_v1`, `palw_claim_lapsed_bound_v1`), used by `palw_state_v2.rs` (frontier prefix),
`palw_security_certification_fold_v1.rs` (prefix + lapsed-credit withdrawal), `palw_rfc0018_v1.rs`, and
`palw_claim_local_rewards_v1.rs`. Validation refuses arming (`validation.rs:324`). Adopted rule (RFC-0023 §3, §7):
bound = `trace_retention_daa`; past it the claim no longer holds the prefix, earns no credit, is not slashed, and its
evidence/reservations stay. No code change was needed; nothing duplicated.

### Stage 2: new per-claim settlement read (connects the existing foundation to a settlement consumer)
The shared gate is `palw_settlement_v1::settled = safe_frontier_daa >= d` (one global frontier: any unresolved A
blocks everyone). The stage-2 foundation (`palw_claim_local_v1`, `_fold_v1`, `_origins_v1`, `_rewards_v1`) already
derives per-claim dependency readiness for held rewards. Added:

- `consensus/core/src/palw_claim_local_rewards_v1.rs`: `pub enum PalwClaimLocalSettlementV1 {Dormant, Settled,
  Held{until_daa}, Denied, NotRetained}` and `pub fn palw_claim_local_settlement_v1(state, params, claim_id, now)`.
  It answers settlement for one claim from that claim and its actual dependency closure (existing
  `reward_readiness_v1`, non-retiring: own Gate C certification, own court/trace windows, prosecution, native EXEC
  dependency, same-execution-root sources visible at admission). Unrelated unresolved claims do not enter.
  `Dormant` below/without the fence (callers keep `palw_settlement_v1` byte-identical); `NotRetained` for a retired /
  unknown id (no guess); `Denied` withholds credit only, never a slash.
- `consensus/core/src/palw_state_v2.rs`: `pub use` re-export of both items.

Test (crate `kaspa-consensus-core`, `--lib`):
- `palw_state_v2::tests::claim_local_rewards_v1::rfc23s2_claim_local_settlement_read_settles_independent_b_while_a_is_unresolved`
  (B settles at DAA 1001 while A is still unbound; C, sharing A's execution root, is Held; Dormant below fence 100 and
  with the fence `None`; NotRetained for unknown id; state root unchanged). Filter: `rfc23s2_claim_local_settlement`.

Fence: reuses `palw_claim_local_settlement_v1` (existing, dormant, validation refuses arming). No new fence, no new
wire/borsh, no new aux row.

### Not done (stage 2 remains incomplete — RFC-0023 §4.5 requires these to change together in one fence)
- No RPC exposes the per-claim read; `palw_settlement_v1`/transaction `settled` is not switched over (needs a
  tx-output → claim mapping; the RFC requires checkpoint/fork-choice/settlement/lifecycle/pruning to change together,
  so switching settlement alone would violate §4.5).
- Checkpoint fold-derived record builder, fork-choice comparator, native lifecycle, pruning/IBD material transfer,
  node drill and §6 campaign: still open (as RFC §7 already records).
- Uncertainty: the test's expectations for `Held` at DAA 129 / `Settled` at 1001 rely on `live_source` holding to
  `max(trace_retention 1000, final+court)` and no EXEC window for attempt-only claims; first compile/run may need
  value adjustments.
