# Independent Source C constructor lifetime review

Reviewed /tmp/g14-source-native-owner-c/source-owner-c.patch and LIFETIMES.md against current A/B-applied source. No repository edits, cargo, RPC or patch application.

No additional coexisting heap owner was found in the successful Source::new_v1 path beyond the C quote plus existing A/B inventories. No corrective patch is proposed from this review. This conclusion is limited to the constructor path, not arbitrary error-formatting/RSS or later numerical/root work.

Verified call/lifetime chain:

1. `PalwPublicTirBindingHeaderV1::resolve_registered_layout_v1` clones registered.program into one binding class raw Vec, and clones layout into that class. Its class/layout identity hashing creates only temporary Borsh layout writer; graph_ir_root hashes bytes directly.
2. `resolve_owned_class_v1` clones job_context into binding, calls verify_tir_binding_v1 at a semicolon and drops its temporary verified result before returning binding. Thus the first verified StepSpace is NOT live when Source::new_v1 performs its independent second verify.
3. verify_tir_binding_v1 first hashes class/layout; `PalwTirStepSpaceV1::new` decodes canonical program and runs validate twice in sequence (decode_canonical validates, then new validates to retain ProgramInfo). The canonical reencoding Vec/validation scratch are covered by A. New retains one parsed program+ProgramInfo and clones layout once. The fixed/hist/commits/occurrences/slotbase vectors, including the transient per-state `layers` Vec, are in B. The binding raw bytes/layout remain live and are the separate C additions.
4. Current successful Source path does NOT call analyze_ranges or an allocating court-cone evaluator. Its `maximum_window_lanes_v1`, `maximum_leaf_lanes_v1`, `cone_runs_bound_v1` and `job_shape` only traverse retained vectors/scalars; floor_sum is scalar. A conservatively includes range/cone analysis families for other paths but C does not need a second range/cone lease for Source construction. Later numerical geometry work is outside this review.
5. `PalwDecodeViewV1::from_tir_header_v1` runs registered length/hash and root/context checks, then clones the job context. It does not decode another program or create StepSpace. At return, binding context, decode-view context and new Source.header context can all be live. C's THREE header.native_heap reservations conservatively cover these three dynamic network_id Vec clones.
6. RUN-sized window_value_bytes collect coexists with the second verified StepSpace, binding and view. q.vec_v1<u64>(RUN) accounts for its Vec capacity. cone_runs is a scalar.
7. Source.hash serializes the header into a Borsh Vec then hashes that borrowed Vec without another byte copy. The Vec drops at that statement before window calculation. class.layout_digest Borsh writer and context_hash CanonicalWriter are sequential, not simultaneous with each other. Context CanonicalWriter writes precisely the context's Borsh-width fields: version u16, network_id u32-prefix+bytes, literal Hash64 fields, seed[32], and three u32 counters. Its initial capacity512 and pinned Borsh initial1024 are both bounded by max(encoded layout/header/context,1024)*2. Canonical program reencoding is independently reserved in A, so co-reserving the C hash writer is conservative.
8. Successful preflight check_program hashing/borrowed scanner/shape counters/native_heap traversal/object_length do not allocate a decoded program or clone class/layout/header before reserve_native_requests_v1. NativeHeapV1's struct traversal has no per-field format-string allocation on successful coverage; overflow/unsupported error strings are a distinct refusal-path concern noted in LIFETIMES.

Ownership interpretation:
- Input registered/layout/header are borrowed and belong to the caller's existing lifetime. C counts newly created clones, not those borrowed original owners again.
- A parsed program/analysis pass and B StepSpace vectors are summed with C raw program/layout/context/result Vec owners, not treated as mutually exclusive.
- The returned NativeRetained<Source> keeps the entire construction reservation. It overholds temporary decode/verify scratch until Source drops; it does not falsely claim those objects remain physically retained.
- The geometric capacity formulas model native requested Rust-owned allocation capacity. They are not a promise about allocator-internal realloc scratch or measured process RSS. No economic/capacity profile follows.

Suggested additional evidence (optional, not a new requirement): compare identity/fields on a real history/ragged layout fixture as well as tiny/two-tile; inspect quote's actual clone-capacity components without merely asserting a positive number. The current structural argument above, rather than self-referential positive quote testing, is the basis of this review.
