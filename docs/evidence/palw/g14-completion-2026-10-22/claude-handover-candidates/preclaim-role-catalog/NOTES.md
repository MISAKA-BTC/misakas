# Native preclaim actual actor catalog — uncompiled /tmp incremental

Base: the three preclaim-origin / original-aggregate / preclaim-requirements candidates combined. Incremental applies cleanly to copied exact requirements files (`git apply --check` exit0). Repository unchanged; no build, native execution or RPC. Test filter remains `g14_native_funded_candidate_fixture_generator_v1`.

This is a substantive existing contract check, not a proposed whole-role assignment algorithm. Actual successful paired prepare plus opt-in native Source enrichment is the only path to prepare_requirements; during that path, before numerical/cover derivation and any FP reserve, a fixed-size actor catalog is derived from the actual native frame/custody contract. Source identity, original producer bond, job/execution/claim, complete original resource plan, custodian upper and exact native terms are checked. The existing pledge validation enforces the existing acceptance upper endpoint (strict) and material horizon. Current actual bond existence, Active status, exact original executor key, operator-key relation and the OLD SourcePledge signature are revalidated. New getter repeats current checks and refuses changed authority after preparation. This does not reinterpret that signature as agreement to new duties.

The catalog contains one *legacy source responsibility* named by the actual pledge, including actual bond/operator/key ID, signed pledge ID and acceptance/material horizons. It contains the native potential-slot count separately, never a vector of guessed actors, never slot0=producer. Actual preclaim has not credited later custody grants or assigned them provider duties; drawn seats/potential slots are not signed responsibility entries. There is no arbitrary manifest constructor, Complete flag, payer consent substitution or caller selected actor set.

Typed missing categories remain: canonical whole-branch actor assignment, shared service operator consent, fee/capital/retention/recovery bodies, and semantic material provider consent when actual plan.semantic exists. They are an iterator over fixed fields, with no allocated set. The successful catalog exposes known legacy contracts while retaining these precise missing new contracts. No new standalone always-Err/helper/entry is added; actual requirements preparation now performs the concrete existing check and retains its fixed-size snapshot. This does NOT implement all-required new-role consent, new consent signature grammar, paid provider acquisition, holding/release obligations, original admission or escrow authorization.

Owner accounting: fixed catalog is stored inline in PreparedOriginalRequirements, whose existing exact<Self>(1) request therefore automatically increases by its actual size. No material/signature/key Vec or BTree catalog clone is introduced. Existing bounded signature/hash primitives are reused; their existing scratch and validation work are not a calibrated native fee/profile and this patch does not claim full work metering. Local source/numerical/input resource errors stay unchanged; catalog failures here are actual fixed original/contract/current-authority failures, not local budget failures.

Actual existing real-key/native-original fixture verifies catalog identity, independent native slot count, typed missing shape and absence of FP/Claim writes. After genuine preparation, three actual state mutations (key rotation, operator mismatch, retirement) independently reject catalog reuse. These do not rely on forged Frame/record/program/roots or public DTO authority. They are uncompiled/unexecuted. No semantic positive is fabricated: actual native prepare still rejects tails, and semantic missing is asserted only according to the existing actual plan.

Limit: a full general all-role native requirements producer still does not exist. This patch deliberately does not infer semantic supply, new operator duty, expense caps or fallback liability from the old pledge. Existing RFC35 approval permits implementing actual known consent checks; it does not supply these absent bodies. The next substantive step must derive those native duties/contracts rather than add a self-signed manifest validator and call it complete.
