# Notification ownership and bounded control state — 2026-11-02

Local audit after retention `7cf9ffe66` / producer readiness `941a865cb`. This patch modifies only `notify/` control-state handling and tests. No data notification is dropped, made bounded or coalesced by this change. It does **not** claim that the remaining notification-data OOM risk is resolved.

## Implemented minimal correction

`Broadcaster::ctl` no longer retains an unbounded sequence of Register/Unregister commands. It retains one payload-free wake and an authoritative `(event, listener ID) → current subscription/connection` map. Register updates the current full scope; unregister removes the entry immediately, including when the worker is awaiting a slow listener. The next control wake rebuilds the plan from a finite snapshot. Memory follows the admitted active registrations and at most one in-flight snapshot/plan, rather than the number of historical commands. There is no new global listener-count or byte limit: the owning service must still bound admitted listeners/scopes.

Each active registration lifetime has an Arc identity token. Scope updates for the same active listener preserve that lifetime; stop then start creates a fresh token. Before starting a send from an old plan, the worker verifies its lifetime is still current. If an old awaited send later fails, its purge removes only that old lifetime, so it cannot remove a restarted listener. A send already in flight may complete on its **old connection**, as before; there is no retry that forwards it to the replacement. A connection replacement for a reused listener ID must go through unregister/start (the owning Notifier fixes its connection for the listener lifetime).

The subscription semantics remain plan-based: an event already being broadcast uses the plan/filter chosen for that event. A later scope update affects subsequent plan reconstruction, not a retroactive re-filtering of an in-flight event. Control wakes remain preferred before the next event, as with the original biased control queue. Coalesced intermediate control states never become an asserted event-delivery history. Ordinary data channels and ordered diffs are untouched.

## Remaining minimal data design (not implemented)

For the internal UTXO consumer, preserving every required change with bounded RAM needs a durable local replay source, not another bounded channel:

1. Record a monotonically identified virtual-change record (before/after tips, diff and reset/import generation) atomically with the corresponding consensus state commit. Write through bounded serialization/spill buffers and an explicit disk quota; a local capacity failure must defer preparation/commit rather than invalidate a valid block or discard a committed diff.
2. Feed only a bounded wake/cursor to the index worker. Read journal pages under a byte lease. Persist the consumer cursor **with** the applied index changes/supply/tips; acknowledge only after successful persistence. Keep records until registered critical consumers have advanced, with coherent reset/reorg handling.
3. Keep external observers separate from that critical retention obligation. A slow external stream needs an explicit lag/disconnect and hash/cursor-based replay or snapshot reconciliation protocol, rather than pinning an unlimited history for every RPC client.
4. Subscription upstream pressure can be addressed separately by passing the Notifier's complete desired compounded state plus a version to Subscriber, then reconciling wildcard/selected-address transitions from its last applied state. This must preserve address-set deltas and errors; blindly keeping the last Mutation is insufficient.

These steps require consensus/index/RPC consumer integration beyond `notify/`. The current index tip is insufficient to implement them solely inside this generic notifier. No journal, durability, cursor, notification bound or external replay behavior is claimed by this commit.
