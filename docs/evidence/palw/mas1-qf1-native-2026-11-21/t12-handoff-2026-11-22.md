## 保存先

同じ Mac 上の永続保存先を以下に示す。DB、モデル入力、holder の作業ディレクトリはローカルで保管する。

```sh
handoff=/Users/wata/.local/share/misaka-t12-handoff/2026-11-22
campaign="$handoff/misaka-fresh-window.5TXzOq19/arithmetic.AOeF8G2s"
generator="$campaign/round16-recovery-work-build.0aOzCogu"
snapshot="$generator/preserved.xbvaVmWy"
```

- 台帳本体は `$snapshot/db`。118ファイルの SHA-256 一覧は `$snapshot/db.sha256`。元の保全コピーと永続保存先の両方を照合した。
- 再生入力は `$generator/through-recovery-parent.jsonl`、生成計画は `$generator/plan.json`、中断までのログは `$generator/native.log`。DB に保存された先端は DAA 51258・blue 102520。入力の読み取り位置は DAA 51259・blue 102522。先端・状態 root・入力のハッシュは[保全記録](round16-preservation-and-short-regressions.json)にある。
- モデル・tokenizer・タイルの入力は `$handoff/inputs`、試験出力は `$handoff/logs`、プロセスの元コマンドと終了状態は `$handoff/processes`。生成時の計画・シェル・ポインタには元の `/tmp` 絶対パスが含まれる。再実行する際はコピーした入力先を指定し、出力には新しい作業ディレクトリを使う。元の plan、署名、close、抽選条件を保全する。

## 再開前にできる検査

T12 worktree のルートから実行する。最初のコマンドは保存ファイル、次の試験は読み取り専用で開いた台帳の先端とブロックアーカイブを照合する。

```sh
(cd "$snapshot/db" && shasum -a 256 -c ../db.sha256)
export CARGO_TARGET_DIR=target/protected-core-tests
export CARGO_PROFILE_DEV_DEBUG=0 CARGO_PROFILE_TEST_DEBUG=0 CARGO_INCREMENTAL=0
export RUST_MIN_STACK=67108864 RAYON_NUM_THREADS=2
cargo +1.93.0 --config 'profile.test.package.misaka-palw-tir-exec.opt-level=3' \
  --config 'profile.test.package.misaka-palw-base0.opt-level=3' rustc \
  -j 2 --locked --offline -p kaspa-consensus --features evm --profile test --lib \
  --message-format=json -- -Cstrip=none -Clink-arg=-Wl,-S > /tmp/t12-handoff-build.jsonl
native=$(python3 -c 'import json,sys; print(next(r["executable"] for r in map(json.loads,sys.stdin) if r.get("executable") and r.get("target",{}).get("name")=="kaspa_consensus"))' </tmp/t12-handoff-build.jsonl)
MISAKA_PRIVATE_GENESIS_SUFFIX_DB="$snapshot/db" \
  MISAKA_PRIVATE_SNAPSHOT_ARCHIVE="$generator/through-recovery-parent.jsonl" \
  "$native" verify_recovery_snapshot_tip --ignored --nocapture
```

読み取り専用の先端照合は通過済み。このコピーから書き込み可能なノードを途中再開する経路は未検証。独立ピアは同じ固定コードと設定で、保存されたブロックをコンセンサスの通常経路から受理する。

## 最後の変更と検証範囲

T12 の当選 fixture に、生成ノードの DAG を別の2つの DB に取り込み、各ノードを再起動して同じ受賞ブロックを再提出する検査を追加した。先端・状態 root の一致と、同一 claim の消費数が1のままかを照合する。

変更前のバイナリでは、当選して手数料が支払われる場合（2.13秒）、落選して権利が発生しない場合（2.16秒）、V3/V4 で同じ権利を二重消費する場合（1.12秒）の各試験が成功した。追加後のビルドは中断され、終了コードを回収できなかった。3ノードに拡張した試験は未実行。途中のコンパイル出力を永続保存先の `logs/misaka-t12-3round-build.{log,jsonl}` に収録した。再開時は上記のビルド後、次のテストを実行する。

```sh
"$native" t12_a_floor_final_becomes_a_permitted_round_block_whose_fee_pays_its_bond --test-threads=1 --nocapture
```

引き継ぎ時に、対象プロセスの終了を PID で再確認した。`processes/at-handoff.json` に確認対象を、`processes/replay-exits.jsonl` と `processes/native39-exit.json` に OS が返した終了状態を保存した。
