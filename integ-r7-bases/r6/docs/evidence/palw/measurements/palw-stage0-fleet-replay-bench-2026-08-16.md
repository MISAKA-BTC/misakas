# Stage-0 fleet replay bench — the first §12 gate artifact with real numbers

**Date:** 2026-08-16 · **Tool:** `palw-worker --mode v2-replay-bench` (iso `949664e`)
**Fleet:** the four live t10 hosts · **Normative:** ADR-0028 §3 (window sizing), §6 (Stage 0)

The first run of the Stage-0 measurement loop on the fleet ADR-0028's windows are sized for.
Every number below is a *measurement artifact*, not a registered value — registration re-derives
windows and the credited ceiling from these per the ADR's own rule.

## 1. Method

* Bench binary built on host B from the `palw-llm-pow-iso` tree (recipe per the x86 class
  calibration: `MISAKA_PALW_CPU=1`, pinned `llama.cpp-cpu` tree, prebuilt static libs, capped
  scope). Distributed to all four hosts alongside a fresh golden set
  (`palw-v2-golden.iso-x86.bin`, generated by the same binary on B — envelope source only).
* Per host, sequentially: `D=16 × 5 runs`, then `D=512 × 3 runs` (host A: 2 runs — it carries
  the live miner at load ≈ 12.7, and its numbers are deliberately its *operational* p99).
  Hosts ran in parallel; root-processes under `systemd-run` scopes (`MemoryMax` 5–6 G).
* Cold process per run (fresh model load), warm OS page cache. GGUF verified at the pinned
  size on all four (still in `/tmp` — still lost on reboot).
* The bench binary's identity (`runtime_class_id 0fc67b41…`, x86 CPU profile of the iso tree)
  is **not** the deployed fleet worker's (`2754900829…`, bps01 profile string) — a measurement
  tool, not a deployment. B's `target-cpu/release/palw-worker` was rebuilt from
  `/root/misakas-v2` afterwards and re-verified at `2754900829bc36f8` so the build tree is
  exactly as found.

## 3. What the numbers say

1. **The credited ceiling is ~10× conservative on measured Q4 numbers.** ADR-0028 §3 derived
   the ≈ 512-decode ceiling from the runbook's 0.75–1.6 s/token — measured on the **F16** 2B
   model in the 120 s block-time decision. The pinned v2 artifact is Q4_K_M, and the fleet
   measures 59–165 ms/token. Extrapolating the slowest host to the FORMAT ceiling
   (D = 4 095): ≈ 11.4 min execute, κ·p99 ≈ 34 min — inside the 1 h window. A
   registration-time re-derivation (exactly what the ADR mandates) may therefore raise the
   credited ceiling substantially; nothing is raised here.
2. **p99 is a per-host fact, not a per-CPU-model fact.** The loaded Broadwell (A) beat both
   idle 8-core EPYC VPSes by > 2× — decode is memory-bandwidth-bound and C/D are shared
   tenancy. Short jobs show the tail clearly: C/D's D=16 p99/p50 reaches 2.2×. This is why
   the ADR demands *measured, per-class, per-fleet* p99 and why a per-token constant would
   under-size windows on exactly the hosts that need them.
3. **Capacity check (§4e)**: at the measured D=512 costs, one replay slot per host sustains
   ≈ 40–95 jobs/h; `R_jobs · q ≤ Σ capacity` holds for every-block crediting (30 jobs/h × q=2
   = 60 duty-replays/h) even with only the two fast hosts — but only just, which is the §4e
   arithmetic doing its job.
